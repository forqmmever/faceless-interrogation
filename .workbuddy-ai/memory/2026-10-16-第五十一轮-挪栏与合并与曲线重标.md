## 一、「透明泳衣原本是整装吗」—— 查证过程

这是本轮唯一一个「先查证再动手」的问题，用户自己也在问。**结论：是。**

三条证据：

**① AU 图包里 `seethroughswimsuit` 上下两份都在。**

```
clothes/under-upper/seethroughswimsuit/   1.png 2.png 3.png 4.png 5.png full.png …
clothes/under-lower/seethroughswimsuit/   full.png frayed.png torn.png tattered.png penis.png
```

**② 与已知成装的形态完全同构。** `dress_nurse` / `dress_cheongsam` 都是
`upper/<款>` + `lower/<款>` 两份；`seethroughswimsuit` 只是把 `upper/lower`
换成了 `under-upper/under-lower`（因为它在内衣目录下）。

**③ 烘到取景框（68×203）之后的 y 范围精密衔接** —— 这是最硬的一条：

| 成装 | 上半层 y | 下半层 y | 接缝 |
|---|---|---|---|
| `dress_nurse` | 48..74 | 74..112 | **74 = 74** |
| `dress_cheongsam` | 49..89 | 85..122 | 重叠 85~89 |
| `dress_leather` | 51..85 | 82..106 | 重叠 82~85 |
| **`seethroughswimsuit`** | **51..88** | **88..101** | **88 = 88** |
| `dress_transparent` | 51..83 | 79..121 | 重叠 79~83 |

→ 结论：**原本就是整装**，于是按用户的话「移到整装」= 把原来拆开的两件**合并**。

★ **踩到的坑：`under-upper/seethroughswimsuit/full.png` 是一张全透明的占位图。**
真实内容在 `1.png`。原 `bra_seethrough` 那条映射只写到目录，靠 `resolve()`
跳过空图后落到 `1.png`；合并时如果照抄「写到目录」，两层里上层就整个消失。
所以新映射**显式点名 `1.png`**。（`dol_prepare.has_content()` 就是为这类空文件准备的。）

## 二、`see: "sheer"` 是刻意给的 —— 别当成顺手加的

新成装带 `see: "sheer"`。原因不是「它看起来透」，而是**数值**：

`EXCLUSIVE_GROUPS = [[["dress"], ["top","bottom"]]]` —— 成装只与**上装/下装**互斥，
**不管内衣**。所以穿上成装后，`bra` / `panties` 两栏还穿着，但会被成装**盖住**
（门控判定为不可见 → 不计暴露/反差）。

也就是说：「合并成一件成装」这件事本身**不会**丢掉内衣那两件的暴露值 ——
但我担心的正是「会不会丢」。算一笔账：

```
合并前：bra_seethrough(9) + panties_seethrough(9) 两件都能计 → 18 点暴露
合并后（不给 see）：成装盖住内衣 → 内衣 0 点，只剩成装自己的 9 点
合并后（给 see: sheer）：成装透出内衣 → 内衣照样计 18 点 + 成装 9 点
```

给了 `see` 之后玩家有两条路都成立：只穿这一件（内衣栏留空），
或者底下继续穿内衣并照样计入。**天花板不会被这次合并压下来。**

## 三、妙妙工具「暂时去掉」的实现取舍

用户说的是**暂时**，所以不能用「删」。做法：把 `"tool"` 加进 `DISABLED_SLOTS`，
**同时把 `MANUAL_SLOTS` 里那条留着**。

有人会觉得「两张表里都有它」是冗余 —— 不是。两者语义不同、且**下架优先**：

```gdscript
static func auto_slots() -> Array:
	var out := []
	for s in active_slots():          # ← 先按 DISABLED_SLOTS 过滤
		if not MANUAL_SLOTS.has(s):   # ← 再滤 manual（tool 已在上一步出局）
			out.append(s)
	return out
```

留着的价值：**恢复只需从 `DISABLED_SLOTS` 里删掉 `"tool"` 一个字符串**，
不用同时记得往 `MANUAL_SLOTS` 里加回来。

★ 连带效果（要如实记）：尼古喵尾那套「带着就不涨怀疑值」的机制
（`Interrogation._add_suspicion()` 读 `GameData.carried_tool()`）**在代码里一行没动**，
但槽位下架后 `WardrobeModel.equip()` 会在模型层直接拒绝它 →
`carried_tools` 恒为空 → **机制实际不可达**。将来恢复槽位，机制自动复活。

### ★ 连带修掉的一个断言写法（两处）

原来有一类对照断言写成：

```javascript
autoSlots().length === active_slots.length - manual_slots.length
```

一张槽位**同时**出现在下架表与手动表里时（`tool` 现在就是），这个式子会**多减 1**。
正确写法是**先求交集**：

```javascript
const manualInAct = (cat.manual_slots || []).filter(s => actSlots.includes(s));
ok(P.autoSlots().length === actSlots.length - manualInAct.length, …);
```

同一处修正做在 `tests/WardrobeTest.gd` 与 `tools/editor_smoke.js` 两边 ——
**这类「两边相减」的对照式，只要两个集合可能相交就是错的。**

## 四、反差曲线：配饰下架凭什么要重标

`CONTRAST_EXCLUDED_SLOTS` 是空表 = 全槽位参与，所以**下架一栏 = 从求和里拿掉一栏**。
配饰栏（暴露 0/1/2 的小件，但**每件都能贡献 0~7 点反差**）整个消失之后：

150 种子 × 4 轮，**真实求解器**（`auto_complete_outfit()`，不是测试里那份
无缺陷约束的 `_dp_optimum`）实测：

| 轮 | 要求 | 最差可达 | 改前余量 | 改后余量 |
|---|---|---|---|---|
| 1 | 125 | 205 | +80 | +80 |
| 2 | 140 | 155 | +30 | **+15** |
| 3 | 155 | 165 | +25 | **+10** |
| 4 | 165 → **160** | 165 | +10 | +0 → **+5** |

150 个种子**全部可解**，但第 4 轮在改前只剩 **+0**（最不利那个原貌只有唯一解）。

★ **为什么第 2 轮掉得最多（30 → 15）**：不是上限问题，是**原貌**问题 ——
第 1 轮原貌 T=7（几乎全暴露）、第 2 轮 T=16…… 越往后原貌越「中间档」，
`Σ|你 − 原貌|` 可拉开的距离越小。所以「删除一件高暴露物品」对不同轮次的影响
**不是均匀**的，必须逐轮实测。

★ **探针的打印有个已知瑕疵**：逐轮汇总那几行里的 `acc` / `cap` 是在**循环结束之后**
才读 `RunData.acceptance_at()`，所以四行都印成 `acc=30 cap=70`。
真正参与求解的 `acc` / `cap` 是在循环内取的正确值（所以 `最差可达` 那列是准的），
但**引用这份日志时别信它的 acc/cap 列**。下次写探针要把那两列一起存进数组。

## 五、截图：这一轮把「分类噪声」的方法补全了

43 张重拍后 `git status` 显示 **30 张**变了。用**两个独立判据**交叉分类
（单靠任一个都会误判）：

### 判据 A：同代码两次跑是否一致

跑第二遍，逐张比「第一遍 vs 第二遍」。**不同的**直接判噪声（渲染非确定性）。
本轮命中 2 张：`06_phone_album` / `07_phone_album_cleared`（SubViewport + 噪点 shader）。

### 判据 B：16×16 块里「过半像素有差异」的块数

- **文字抗锯齿**：差异只在字形描边上 → 稀疏 → 这种块 **≈ 0**
- **真实 UI 变化**（换装界面少一栏、卡片减一张）→ 成片 → 这种块 **≥ 8**

本轮结果：`01b` 205 块 / `01c` 188 / `01d` 188 / `01g` 8 → 真变化；
其余 26 张 **0~5 块** → 文字抗锯齿。

### ★ 本轮最大的坑：`--import` 会重烘字体图集

这一轮跑了 `--import`（新贴图要导入），于是**字体图集被重烘** →
**所有含文字的镜头相对上一版都有细微抗锯齿差异**。

这解释了为什么「30 张变了」里有 26 张是噪声 —— 而且它们**同代码两次跑完全一致**
（判据 A 抓不到），只有判据 B 能看出来。

★ 结论：**判据 A 单独用不够**。运行 `--import` 之后重拍截图，
一定要补判据 B，否则会把 26 张字体噪声全提交进去。

本轮实际只提交 **4 张**（`01b_briefing_bottom` / `01c_gate_hidden` /
`01d_gate_shown` / `01g_tattoo_multi`）。

## 六、几何阈值：底边 104 → 95（重新实测，不是放宽）

新成装 `dress_seethrough` 底边只到 **101**，被「成装必须覆盖上下两截」那条
第 49 轮加的几何断言判为不合格。要不要调阈值，先把两类样本的真实分布量出来
（只取 col0，与 `crop_clip` 一致）：

| 类别 | 底边 |
|---|---|
| **只叠 `upper` 一层**（第 49 轮那个 bug 的形态） | 74 / 89 / 85 / 88 / 83 → **74..89** |
| **两层都叠**（正确） | 112 / 122 / 106 / **101** / 121 → **101..122** |

两段之间只有 **89 → 101** 这 12 px 空档 → 取中点 **95**。

取 95 之后：每个「只叠 upper」的样本仍被抓出（最高 89 < 95）——
**断言没有失去作用**；最短的合法成装（101）留 6 px 余量。

★ 这套做法值得复用：**要动一个「实测标定」的阈值时，先把两类的真实分布重新量出来，
找接缝、取中点，并确认「原本要抓的样本仍被抓到」。** 直接往下拽阈值 = 把断言变成摆设。

## 七、第 51 轮的教训汇总

1. **「一整件被拆成两半存」有两个独立证据**：源图目录成对存在 + 烘完 y 范围精密衔接。
   只有第一条不够（目录可能只是命名巧合）；y 衔接是硬证据。
2. **显式点名文件**：目录里可能有全透明占位图（`full.png`），写到目录会挑错帧。
3. **合并物品时要算「盖住 / 透出」那笔账**：`see: sheer` 决定内衣的暴露值还算不算。
4. **两张名单里出现同一个槽位不是冗余**，而是「下架优先 + 恢复只动一处」。
5. **「两边相减」的对照式在两个集合可能相交时是错的**，要先求交集。
6. **`--import` 之后重拍截图必须补判据 B**（16×16 实心块），否则字体噪声会漏进提交。
7. 探针的汇总打印别在循环外读运行时状态（本轮 `acc`/`cap` 列因此失真）。
