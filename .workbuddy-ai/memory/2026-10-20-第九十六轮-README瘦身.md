# 第九十六轮：README 瘦身 6253 → 2576 行，并给它一个检查节点（2026-10-20）

## 一、起因

用户口径：「readme应该怎么改 下次我应该怎么设置readme的读写」。

第 95 轮删 `交接.md` 时顺手量了一下，README 是 **6253 行 / 434 KB** ——
比 `CHANGELOG.md`（173 KB）+ `REFERENCE.md`（51 KB）加起来还大。

## 二、三类病（都有实据，不是感觉）

### 1. 逐轮历史与 CHANGELOG 重复

README 里有 16 个 `## 第七十五轮：…` 到 `## 第九十二轮：…` 的小节，合计 **1489 行**。
逐个核对：CHANGELOG 里**每一轮都有对应小节**（第 75 轮 4 处、第 80 轮 6 处……）。

★ 但**不能直接删**：逐轮对比字符数，README 版**每一轮都比 CHANGELOG 版详细**
（合计 51751 vs 18497 字符）。所以它是「第二份更详细的 CHANGELOG」，不是摘要。

更隐蔽的是：`## 美术资产（小人 · AU 图包）` 这个标题底下，藏着
`### 第三十四轮：…` 到 `### 第四十九轮：…` 共 **1363 行**物品补充记录 ——
标题叫「美术资产」，内容全是逐轮记录。`## 内衣内裤的曝光门控` 底下同样混着
第二十四~二十七轮的 605 行。

★★ **这是 README 膨胀的真正模式：在功能说明节下面追加当轮记录。**
每轮都只加几十行，看着不多，30 轮下来就是 1000+ 行。

### 2. 过期数字自相矛盾

断言数在 README 里被手写了 **11 处**，共 **6 个不同值**：

| 值 | 出现次数 |
|---|---|
| 606 | 4 |
| 938 | 3 |
| 937 | 1 |
| 1512 | 1 |
| 1762 | 1 |
| 1915 | 1 |

实测是 **572 / 745 / 337** —— 全部过期。而且 606 与 600（`1512 = 600 + 912` 里那个）、
938 与 937 自己就跟自己打架。

★★ **同一份文档里手写同一个数字 11 次，改一处忘十处，是必然的。**

### 3. 无组织的墙

- `## 核心玩法` 1710 行，只有 2 个 `###` 子节（阶段一 / 阶段二）
- `## 美术资产` 1564 行，`###` 子节下全是逐轮记录

## 三、处置

| 删掉 | 行数 |
|---|---|
| 16 个「第 75~92 轮」小节 | 1489 |
| 曝光门控下混装的第二十四~二十七轮物品记录 | 605 |
| 美术资产下混装的第三十四~四十九轮记录 | 1363 |
| 后续可扩展方向里 24 条「~~已完成~~」的条目 | 221 |
| **合计** | **3677** |

结果：**6253 → 2576 行（-59%）、434 KB → 200 KB**，12 个二级标题一个没少。

### 搬家（两条确实独有，没丢）

1. `Array or []` 在 GDScript 里非法 / 测试脚本别用 Python 的 `repr()` /
   删调试 `print` 要连跨行后半截一起删 → `REFERENCE.md` 二章
2. 第四十九轮「成装只有上半身活了 12 轮」的方法论（断言查「存在 / 非空」
   看不出「少做一步」，只有几何 / 数值范围能看出来）→ `REFERENCE.md` 十四章

### 断言数字的处理

一律不写进 README，改成「以跑出来的为准，历次见 `CHANGELOG` 末尾表」。
耗时表从 3 列压成 2 列（去掉具体秒数，只留「怎么压下来的」）。

## 四、交付物：`tools/readme_check.py`

这是本轮真正的东西 —— 用户问的是「下次怎么设置读写」，答案不能只是一段文字，
得有一个**每轮能跑、跑完给结论**的节点（否则就是重犯 `交接.md` 的错）。

五类检查：

1. 带「第 N 轮」字样的小节（属于 CHANGELOG）
2. 单节超 250 行
3. 假标题（代码块围栏坏了，注释跑成标题）
4. 断言数字与 `CHANGELOG` 末尾测试表的最后一行比对
5. 总量涨过基线 10% 就报

★★ **写这个脚本自己踩了两个坑**：

- **没跳代码块围栏** → 一条 shell 注释 `# 新烘出来的 png 要跑一次导入…` 被当成
  一个 **1395 行的一级标题**，于是「美术资产」那节的行数怎么算都不对。
- **「单节超 250 行」的判据太粗** → 删完历史后，`## 核心玩法` 剩 1105 行但拆成了
  30 个 `####` 子节（每节最大 87 行），被误报成「墙」。
  改成：**节内有子标题就按最大子节算，没有才按整节算** —— 这才对应
  「1710 行只有 2 个子节 = 没组织」和「1105 行有 30 个子节 = 组织过」的区别。

★ 全文预算从「理想值 1500 行」改成「**基线 2576 + 允许涨 10%**」。
设理想值只会每轮都报错，报多了就没人看了。

## 五、改了两条规矩（根因就在规矩里）

`MEMORY.md` 收尾第 2 条原来是：

> `README.md` 写「为什么这么改 / 机制 / 数值表 / 踩坑」

★★ **这条就是 README 膨胀的根因。**「为什么这么改」和「踩坑」属于 CHANGELOG，
写进 README 就变成了第二份 CHANGELOG。

现在改成：

> `README.md` —— **只写「现在是什么 / 怎么用」，不写「为什么这么改」**。
> 三条判据：带「第 N 轮」字样的段落不进 / 会过期的数字不进 / 单节超 250 行就拆。
> 改完跑 `python tools/readme_check.py`。

`AGENTS.md` 的收尾同步加上这个脚本。

## 六、教训

★★ **文档膨胀的根因从来不是「写得多」，是「写在了错的地方」。**
这 3677 行没有一行是废话 —— 它们都是 CHANGELOG 该收的东西，只是被放进了 README。
所以处置方式不是「写少点」，是**给每份文档划死职责边界**。

★★ **同一个数字写 11 次，等于没有数字。** 会变的事实只留一份权威源，
其余地方写「见某处」，或者干脆让工具去数。

★★ **「以后小心点」不是机制。** `交接.md` 烂了 37 轮、README 涨到 6253 行，
都不是因为谁不小心 —— 是因为**没有一个每轮都会跑的检查**。这次补上了。

## 七、删章节的连带成本：5 处交叉引用失效

删完之后 `grep` 那些章节名，发现 5 处「见下文 / 见上面某节」指向已经不在的东西：

| 原引用 | 实际情况 |
|---|---|
| 「为什么这么改 → 看**本文件对应的轮次章节**」 | 轮次章节已删（这轮删的） |
| 「详见上面「手机（第五十五轮起并入文本编辑器）」」 | 标题已改成「手机」（这轮改的） |
| 「见下文「轮次与曲线」」 | **这一节从来就不存在** |
| 「见上面「盘问中掏手机」」 | 实际标题是「📱 掏出手机（盘问里也能查档）」 |
| 「见下文「怀疑度的来源」」 | 实际是「怀疑度机制」，而且**在上文**不是下文 |

★★ **后三条不是这轮弄坏的**，是早就失效的。说明「交叉引用」这类东西没人查就会一直烂，
而且**没有任何测试会报它**（`readme_check.py` 现在也不查 —— 要查得解析标题做匹配，
成本不低；先靠人工 grep）。

★ 规矩：**删章节时先 `grep` 那个标题名**，看谁在引用它。已写进 `MEMORY.md` 收尾第 2 条。
