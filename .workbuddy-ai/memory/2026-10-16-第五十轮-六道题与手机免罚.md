## 一、掏手机数值：为什么是「免罚 1 + 单价 8」

先说清**现状其实是个错觉**。改之前是 `PHONE_PULL_FREE = 3`、`PHONE_PULL_PENALTY = 15`，
越界第 n 次罚 `15 × n`：

| 掏出次数 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 累计怀疑度（起点 20） | 20 | 20 | 20 | **35** | **65 过线** | 110 |

**「免罚 3 次」只兑现出 1 次宽限** —— 第 4 次那 +15 是唯一真的兑现在 40 点预算里的一笔，
到第 5 次 +30（扣掉前面已用的 15，还剩 25）直接 65 > 60（通过线）。

账要这么算：`pass_suspicion = 60`，第 1 轮起点 20 → **一轮总共只有 40 点预算**。
而单次代价里已经就位的：前后矛盾 **35**、QTE 失败 **24**、盲区硬答 **24**、干扰没拦 **18**。
`15 × n` 在这张表里属于「中档偏贵」—— 一次越界就抵掉大半个矛盾。

**只降免罚、单价不动会毁掉这个功能**：

| 掏出次数 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 免罚 1 + 15×n | 20 | 35 | **65** | 110 |

第 3 次掏出就过线 —— 一轮只能掏 2 次。可一轮 6 道题里「**必看的**」就有 2~3 次：

- 盲区题：正解**只能**从手机备忘录第一条推出来（不翻就是纯赌性情）
- 说法题 / 同行者题：要对上短信里的官方口径，记不住就得掏出来看一眼

→ 手机当场变成废功能，玩家只能硬背。

**免罚 1 + 单价 8**（本轮定的）：

| 掏出次数 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 累计（起点 20） | 20 免罚 | 28 | 44 | **68 过线** | 100 |

掏出 3 次累计 **24**（20 → 44，余 16），「必需的 2~3 次」刚好落在安全线内；
第 4 次 +24 累计 48 → 68 过线。**想多瞄几眼就得拿别处的容错去换。**

考虑过但没选的两种：

- **两段式**（首罚 5、之后每次 +15）：第一次被看见几乎不疼，从第二次起明显加重。
  需要在 `rules` 里新增字段，改动面大；效果与单价 8 接近。
- **单价 12**：掏 3 次到 56，余量只剩 4 点 —— 等于「掏 3 次就别再犯别的错」，
  一盘 6 题没有容错空间，太紧。

## 二、每轮题数 8 → 6

`QUESTIONS_PER_LEVEL` 8 → 6，同步 4 处：`Interrogation.gd` 常量、`ScenarioData.DEFAULT_RULES`、
`data/story.json` 的 `rules`、两个编辑器快照（`story_editor.html` / `phone_editor.html` 内嵌 seed）。

**编排没动**，仍是 `RunData._questions_for_level_v1()`：

```
本轮固定题（level == li：说法 1 + 同行者 1 + 盲区 1）
  + 跨轮复问（li > 0 时排 1 道 recall）
  + 从通用池补足到 count
```

- 第 1 轮：3 固定 + 0 复问 + 池补 3 = **6 道**（档案题 3）
- 第 2~4 轮：3 固定 + 1 复问 + 池补 2 = **6 道**（档案题 2）

**池子够不够**：出厂每套背景 24 道题 = 8 道通用档案题 + 4 fact + 4 recall + 4 companion + 4 blind。
四轮各取 3/2/2/2 = 9 次抽取，但**每轮独立洗牌**（各自用 `_level_rng(li)`），
所以不是「累积消耗」，每轮都能从完整 8 道里取 —— 够用。（这一点容易想错，记一下。）

**★ 连带影响：档案题两类（A / B）都出现的概率降了。**
从 8 道池里抽 3 道，抽到**全是同一类**的概率 = `2 × C(4,3) / C(8,3)` = **14.3%**。
`TestRunner` 里那两处「找一道 A 类题 / 一道 B 类题」的断言因此**必须留着跨关、跨局的兜底**
（`_find_level_with_card_owner`：先在当前局 4 关里找，找不到再换 80 个种子）。
改题数时差点把这条兜底当成冗余删掉 —— 它是承重的。

## 三、取消「他给你发短信」

`_phone_pull_event()` 改前 vs 改后：

```gdscript
# 改前
var text := ScenarioData.interrogator_sms_at(n - 1)
if text == "":
    return                      # ★ 隐患：取不到文案 → 整个事件静默失效
GameData.interrogator_sms.append(text)
shake(...)
_add_suspicion(penalty)
...phone_notice 用 [RunData.interrogator(), text]（2 个占位符）
...phone_caught 用 text（1 个占位符）

# 改后
var penalty := _rf("phone_pull_penalty", PHONE_PULL_PENALTY) * float(n)
shake(_rf("shake_phone_caught", 7.0), 0.32)
_add_suspicion(penalty)
if _ended: return
...phone_notice 用 [int(round(penalty))]（1 个 %d）
...phone_caught 不带占位符
```

**★ 顺带修掉一个隐患**（这是本轮最有价值的一处发现）：
旧代码是「取不到短信文案就直接 `return`」—— 也就是说**编辑器里把那 5 条文案删掉或改空，
整个越界惩罚就静默失效**：不震屏、不涨怀疑度、也不弹提示。
玩家什么都看不出来，只会发现「掏手机不要钱了」。现在数值与文案彻底解耦。

**文案怎么处理**（用户选「文案留着，只是不再发」）：
那 5 条 `interrogator_sms` 留在 `story.json` 里，`tools/phone_editor.html` 照旧能改，
`PhoneDesk.INTR_THREAD` 那条线程照旧能渲染。只是没有东西往里写 →
正常流程里它是空的、**整个分组都不显示**（`PhoneDesk._build_message_list` 里 `if not ...is_empty()` 跳过）。

`tests/Screenshot.gd` 的 `09_phone_interrogator_sms` 镜头是**直接塞数据**拍的
（`gd.interrogator_sms = [...]`），所以不受影响 —— 只改了注释说明这件事。

## 四、连带改的 5 处文案（★ 占位符改动的完整链路）

| 字段 | 改动 | 为什么 |
|---|---|---|
| `ui.interrogation.phone_notice` | `2 个 %s`（发信人 / 短信内容）→ **`1 个 %d`**（本次涨多少） | 不再引用短信正文，改成报数值 |
| `ui.interrogation.phone_caught` | `1 个 %s` → **`0 个`** | 那句不再引用短信正文 |
| `ui.interrogation.phone_tip` | 「掏太多次他会发现」→「**第二次掏出来，他就看见了**」 | 免罚降到 1 次要如实告知 |
| `phone.messages.interrogator_tail` | 「每次你把手机掏出来看，这条线就会再长一句」→「**这条线只会变长，不会变短**」 | 原句直接描述已被取消的机制 |
| `ui.help.phone_marks`【消息】段 | 「**三段**排下来：审问官本人（...）、同行的人 C、朋友」→「**两段**排下来：同行的人 C、朋友」 | 那条线正常不出现 |

### ★ 占位符改动 = 改接口，有 4 个地方要一起动

1. 调用点 `_tf(...)` / `_ut(...)` **参数表**（少一个参数 → 运行时 `not all characters converted`）
2. `ScenarioData.gd` 的 `DEFAULT_*` 兜底
3. `data/story.json`（游戏**实际读的**）
4. **★ `tools/story_editor.html` 的字段声明表** —— 本轮新踩到的：
   ```js
   A("phone_notice", "掏手机时弹出的小通知", 2, "带 1 个 %d：本次涨了多少怀疑度", true),
   A("phone_caught", "掏太多次被发现的提示", 4, "不带占位符 —— 第五十轮起这句不再引用短信正文"),
   ```
   `A(k, label, rows, hint, ph)` 的第 5 个参数 `ph: true` 表示「**必须含 %**」。
   校验代码：`if (f.ph && !String(val).includes("%")) err(... 丢了占位符 ...)`。
   `phone_caught` 改成 0 个占位符后，`ph` 必须去掉，否则 `editor_smoke.js` 报
   「界面文案 · 阶段二 · 盘问界面 · 掏太多次被发现的提示 丢了占位符（%s / %d）」——
   **而且它连带挂两条断言**（「0 个错误」+「改数值后校验依然 0 错误」），
   看起来像两个 bug，其实是同一处根因。
   ★ 这条守卫只判「有没有 %」，**不判个数** —— 所以 `ph: false` 之后，将来往
   `phone_caught` 里写 `%s` 不会被抓。已知局限，本轮不扩大改动面。

## 五、改两个编辑器快照的办法（不用重跑 DumpStory）

`rules` / `ui` 段是**逐键覆盖**语义（不是整段替换），所以只改 `story.json` 里的几键时，
可以直接改两个 HTML 里的内嵌 seed，**不用重跑 `DumpStory`**。

```bash
# ① 先验证「解析 → 紧凑重序列化」是否逐字节还原（不还原就别这么干）
python .workbuddy-ai/tmp/probe_seed_roundtrip.py
#    实测两个文件都是 106059 字节、往返一致 = True
# ② 再改字段
python .workbuddy-ai/tmp/patch_editors.py
```

**★ 踩到的坑：两处比较方式不同，不能共用同一对字符串。**

- `story.json` 的**原始行文本**里，换行是**字面的 `\n`**（两个字符）→ 用子串 `in` 匹配
- JSON 解析后的**值**里，换行是**真实换行** → 用全等 `==` 匹配

本轮第一次跑 `patch_copy.py` 时两者混用，结果 `phone_tip` / `tail` 改成功了、
`help.phone_marks` 那条**静默漏掉**（`walk_patch` 用 `==` 比不过带字面 `\n` 的串）。
所以脚本里维护了两套：`RAW_PAIRS`（字面 `\n`，给行替换）与 `VAL_PAIRS`（真实换行，给 JSON 值）。

**★ 还有个坑：脚本要写成幂等的。**
第二次重跑时 `phone_tip` 与 `tail` 已经是新值，`old` 命中 0 处 → 脚本直接 `sys.exit(1)` 报 ABORT。
改成「**新值已在行里就跳过**」之后才能安全重跑。

## 六、测试：刻意让四套数字「一个都不变」

改动动了运行时行为，按规矩跑了全套。但**断言条数是刻意保持不变的**：

- 手机那一段（`TestRunner._test_phone_in_interrogation`）：原来 26 条 → 现在 **仍 26 条**。
  做法是**逐条替换**：旧的两条「收到短信 / 短信有正文」换成「★ 不再收到他发来的短信」，
  新增的 4 条（第 1 次免罚怀疑度没涨 / 第 1 次越界恰好 8 / 第 2 次恰好 16 / 通知条写明涨了多少）
  由删掉的 4 条旧断言（「前 3 次他不会发消息」「第 3 次仍在免罚额度内」「两条短信内容不同」
  「他发过的短信留在手机里」）腾出位置。
- 档案题条数门槛「≥3」→「≥2」（6 道题时第 2 轮起只剩 2 道档案题）。
- 题数断言从写死 8 改成动态：`size() == Interrogation.QUESTIONS_PER_LEVEL`、标题用 `%d`。

**为什么在意这个**：断言数一变，README 里十几处「（N 项断言）」「Checks: N」都要跟着改，
还容易漏。**能在不改总数的前提下改断言，就尽量改。**

| `TestRunner.tscn` | **912 / 0** |
| `editor_smoke.js` | **239 / 0** |

| `Screenshot.tscn`（43 张） | **0 报错** |
| `tools/flow_overview.py` | 重生成 |

★ `flow_overview.py` **又一次**差点漏掉（它不在五套验证里）——它的图注表里

## 七、截图：43 张里 5 张是噪声（排查过程值得记）

重拍 43 张后 `git status` 显示 **5 张**变化。按文案改动，**应该只有 2 张**
（`00e_help_phone` 帮助浮层 / `09_phone_interrogator_sms` 线程底部提示）。另外 3 张是
`06_phone_album`、`07_phone_album_cleared`、`25_run_failed` —— 本轮**没有**任何改动能解释它们。

### 排查：日志相同、但图不同

先比两次截图的**完整日志**（`shot2.log` 是第 49 轮那次，`shot50.log` 是本次）：

```
$ diff shot2.log shot50.log
96c96
< --- 9: 手机 · 盘问里掏了 4 次 → 收到审问者本人的短信（红框那条）---
---
> --- 9: 手机 · 审问者本人的短信（红框那条）---
```

**只有 1 行不同，就是我自己改的那句 `_plog` 文案** —— 其余 96 行逐字相同。
（判据③「`_plog` 逐字相同」成立 —— 但相册那两段**没有 `_plog` 输出**，
所以这条判据在这里使不上劲，它只打印脚本主动打印的东西。）

### 定性：与「同代码两次跑」比量级

再跑一次截图，拿「同代码两次跑」的差异当**基准尺度**：

| 对比 | `06_phone_album`（差异像素 >0 / >8 / >40） | `07_phone_album_cleared` |
|---|---|---|
| 旧版 vs 本轮 | 22000 / 14223 / 1895 | 15528 / 2614 / 0 |
| **同代码两次跑** | **21998 / 14261 / 1856** | **15542 / 2759 / 0** |

**两组数字几乎完全一样** → 差异**全部**来自渲染噪声，不是回归。

`19_expression_qte` / `20_leak_exposed` 用同法验证，更直接：第三次跑时它们与旧版不同，
**第四次跑时与旧版逐像素一致** —— 同一个文件跑两次能一次一样一次不一样，
确定性根本不成立。它们是**抖动（`shake`）+ 动画进度条**导致的位移。

### 结论与处理

| 镜头 | 为什么会变 |
|---|---|
| `06` / `07` 相册 | 照片在 `SubViewport` 里实时渲染，噪点 / 模糊 shader 每次采样相位不同 → **整块照片区**都变 |
| `19` QTE / `20` 说漏嘴 / `25` 失败页 | 带抖动位移 + 进度条停在的帧不同 → 大面积**稀疏**差异 |

**处理：`git checkout --` 还原这 3 张（`06` / `07` / `25`），别把噪声提交。**
最终本次只提交 **3 张**真正变化的：`00e_help_phone` /
`09_phone_interrogator_sms`（差异 bbox 正好是那 11 px 高的一行提示） / `_flow_overview.png`。

★ 这个判据已经写进 `REFERENCE.md` 的「截图判据」节 —— **原三条判据（针对字体图集重烘）
管不住这类镜头，判据①「连跑三次一致」在它们身上必然失败**，
所以必须补一条「**与旧版差异量级 ≈ 同代码两次跑量级 ⇒ 噪声**」。

## 八、下一轮的待办（用户本轮追加的需求）

> 「下一轮编辑器可以新增背景，不止现有的四个，点击开始游戏的界面同步更新」

拆解（下一轮开工前先确认边界）：

- **编辑器**：题库页现在按「背景」分节，要能**新增 / 删除背景**（现在是固定 4 套：
  边境哨卡 / 城镇驿站 / 公爵府邸 / 港口海关）
- **开始界面**：背景选择/展示要随数据变（现在应该也是写死 4 个或按 `background_ids()` 走）
- 涉及面：`ScenarioData.background_ids()` / `background_name()`、`OutfitData.DEFAULT_LEVELS`
  与 `ScenarioData.DEFAULT_LEVELS` 的同步、`tools/story_editor.html` 的背景页、
  `Main.gd` 的开始界面、新背景的 `facts / sms / questions / companion_sms / true_name / endings`
  **一整套必填字段**（`WardrobeTest` 有「每套背景都配齐」的断言守着）
- ★ 已知硬约束：每套背景的 `facts` 数要 ≥ `OutfitData.MAX_LEVELS`（4）、
  `sms` ≥ 3、`companion` 题 ≥ 3、`questions` 数 ≥ 每轮抽题数（现在 **6**）——
  新增背景时这些都要一次配齐，否则 `WardrobeTest` 当场挂。
- ★ 新增背景的**审核**（用户在界面上的入口）与**存档兼容**（`RunSave` 里存了背景 id，
  删掉一个背景后旧存档怎么办）也要一起想。
