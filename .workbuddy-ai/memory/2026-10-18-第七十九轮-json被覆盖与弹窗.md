# 第 79 轮：为什么 story.json 老被覆盖 + 编辑器弹窗口

日期：2026-10-18
用户两问：
① 「为什么每次更新都会把我之前的更新的 json 覆盖掉」
② 「为什么打开编辑器会弹一个必须手动关闭的窗口」

## 一、窗口 = 服务本身

`start "story-editor-server" /min python ...` 起的是 **python.exe**，它带控制台 ——
`/min` 只是最小化，不是隐藏。所以屏幕上永远多一个黑窗口，关掉它 = 停服务。
这就是「必须手动关闭」的那个窗口，不是报错窗口。

**修法**：bat 里找同一个解释器旁边的 `pythonw.exe`（无控制台版），用它起服务：

```bat
set "PYW="
for %%D in ("%PY") do if exist "%%~dpDpythonw.exe" set "PYW=%%~dpDpythonw.exe"
if not defined PYW set "PYW=%PY%"
if "%PYW%"=="%PY%" (
    start "story-editor-server" /min "%PY%" ...
) else (
    start "" /b "%PYW%" ...
)
```

没有 pythonw 时仍退回最小化窗口（不能保证 100% 无窗口）。
**代价**：没有窗口可关 = 用户失去「停服务」的把手 → 新增 `POST /api/quit`
+ 编辑器顶栏「⏹ 停服务」按钮（`server.shutdown()` 在后台线程里调，不能在同一线程调）。

另外把两处 `pause` 改成 `ping -n N` 倒数自动退出（失败提示 20 秒、找不到 python 10 秒），
失败时也不会留一个等人按键盘的窗口。

## 二、json 被覆盖的三条真实机制

### 机制 A：我这边整份重写（第 78 轮真发生过）
`json.loads → 改 → json.dumps` 重写整个文件。第 78 轮那次把 6 套写成 3 套旧版
（diff 2258 行），连第 74 轮的文案回退都被带走。**已改成逐行文本删除 + 写后校验背景数。**

### 机制 B：编辑器页面开着，磁盘被改，按保存 → 整份盖回去（★ 最主要的那条）
时间线：
1. 你打开编辑器 → 页面把当时那份 JSON 读进内存；
2. 磁盘上的 `story.json` 被改（我改代码、git 切分支、你在另一个标签页存的）；
3. 你在**还开着**的旧页面上改一处 → 保存 → 整份「旧内容 + 这一处」写回去，② 全没了。

**修法（If-Match 版本号）**：
- `GET /api/story` 回一行 `X-Story-Rev: <sha256 前 16 位>`；页面 `boot()` 记进 `loadedRev`；
- 保存时带 `If-Match: <loadedRev>`；服务端与磁盘当前 rev 不一致 → **409 拒收**，附上当前 rev；
- 页面收到 409 只更新 rev、不写盘，提示「磁盘已经变了，点 ↻ 重新载入」；
- 新增「↻ 重新载入」按钮（带未保存改动时二次确认）；
- ★ 只在**请求带了 If-Match** 时才校验 —— curl / 脚本照旧能直接写。

### 机制 C：`tools/DumpStory.gd`
它从 `ScenarioData` 的**当前值**重新生成整份 json。`backgrounds[].questions[]` 是第 29 轮
迁移进去的，代码里没有 —— 一旦重跑，题目/结局/背景页的编辑全被冲掉。
**规矩**：只改 `rules` / `levels` / `true_presets` 这类段**不要**跑 DumpStory；
不确定就别跑，用编辑器改。

### 额外保护：时间戳备份
每次写盘除了 `story.json.bak`（只有一份，覆盖两次就没了），再往
`data/backups/story-YYYYMMDD-HHMMSS.json` 留一份，只保留最近 30 份，已加进 `.gitignore`。
出事了能翻回去。

## 四、冒烟里清掉的那批「旧断言」
用户只剩 3 套背景（border_post 自动 + scene_1 / scene_2 自行编辑，且都已启用），
原来按「6 套 / 4 套启用 / 情景一二是草稿」写死的断言全部失效 —— 逐条改成**规则型**：

| 原断言 | 改成 |
|---|---|
| 恰好 6 套背景 | 报出实际套数 + id 列表 |
| 启用 = 4 套 | 启用数 == 没被标草稿的套数 |
| 情景一/二是草稿 | 草稿标志值合法 + 与「是否参与抽取」一致 |
| 启用背景全是 auto | 每套题源是合法值（auto / manual） + 报 manual 套数 |
| 草稿提醒 = 2 条 | 草稿提醒数 == 标成草稿的套数 |
| 每套 27 条结局文案 | 报告 N/27，不判失败（字段表固定 27 项，缺的回落出厂） |
| `backgrounds[1].cards[0]` | 挑「真的有卡」的那套（manual 背景没有卡，会抛 undefined） |
| 盲区题字段齐全 | **manual 背景整段跳过**（运行时的 `is_blind` 也排除了它们） |
| 短信 level 在 facts 范围内 | 没有 facts 时只查「非负整数」 |
| 「0 条提醒」守门人 | 只对 **auto 背景**生效（manual 的结局文案没填完是数据现状，不是毛病） |

剩下 2 条属于用户数据本身，不是代码问题：
- `scene_2 的「与朋友」有短信（0 条）` —— 那套背景确实还没写朋友短信；
- 「清空 4 条文案 → 一条都不提醒」这个负向用例被「通用池是空的」等 57 条真提醒淹了 ——
  该负向用例需要先在一条**干净**的背景上跑。
