# 第八十五轮：同暴露值的不同件也算反差（+2 / 发型 12 / 妆容 10）

用户口径三句话：
1. 「同暴露值的不同件衣服增加 2 分，发型、妆容多加点」
2. 「不要改这个强制上装」（scene_1 第 1 轮的 `top_school_navy` / `bottom_school_navy` 原样保留）
3. 「现在第一轮的反差值和接受度设置，是否能满足需要一点操作，观察相册和原貌然后又有足够多的配装方式」

## 一、改了什么

### `WardrobeModel._contrast_of`

```gdscript
var v: int = absi(now_exp - base_exp) * int(data.contrast_per_exposure())
if base_id != "" and id != base_id and now_exp == base_exp:
    v += data.contrast_same_exposure_bonus(slot)
```

加的两个条件都很关键：
- **`now_exp == base_exp`**：暴露值不同的话前半截已经在给分，再加一档 = 同一件事算两遍；
- **`id != base_id`**：穿回原貌那一件必须仍是 0（「和他记得的一模一样」不算伪装）。
  ★ 这也是 `base_id == ""`（原貌那一栏没穿 / 没戴）时**不加分**的原因 —— 那种情况
  「基线 = 0」本来就没有「原貌那件」可比。

### 三个数值键（`ScenarioData.DEFAULT_RULES` + `story.json` + 编辑器）

| 键 | 值 | 说明 |
|---|---|---|
| `contrast_same_exposure_bonus` | 2 | 其余槽位统一 |
| `contrast_bonus_hair` | 12 | 发型 7 件全是暴露 0 |
| `contrast_bonus_makeup` | 10 | 妆容 6 件里 5 件暴露 0 |

★ **一开始写的是字典键 `contrast_bonus_slots: {"hair":12,"makeup":10}` + `rule_dict()`**，
后来改成三个标量 —— 因为编辑器「数值规则」页只认标量字段（`t:"num"`、`t:"strlist"`），
字典要另做一种字段类型才填得进去。标量三个键的代价只是多两行，换来直接可编辑。

★★ **编辑器里原本根本没有「反差」这一节**：`contrast_per_exposure` / `contrast_req_base` /
`contrast_req_step` 三个键一直在 `DEFAULT_RULES` 里，但「数值规则」页从没列出来
（当年写的是「服装相关，留到下一轮」）。所以在编辑器里改不到这几个数 —— 这次补了
「⑥ 反差」一节 6 项，`rulesSections()` 长度 30 → 36。

## 二、scene_1 第 1 轮：能过了，但只有 1 分余量

强制校服把 `top` 锁在 `top_school_navy`（暴露 0 = 原貌 `top_sailor_white` 的暴露 0），
**这一格以前恒为 0 分**。上限就在这里丢的。

```
改前 DP 最优 105（要求 125，过不了）
改后 DP 最优 126（要求 125，刚好过）
```

6000 个合法搭配里：

| 要求 | 能过 | 通过率 | 不同搭配 |
|---|---|---|---|
| 125（现在） | 9 | 0.1% | **5 条** |
| 115 | 155 | 2.6% | 86 条 |
| 110 | 374 | 6.2% | 214 条 |
| 105 | 739 | 12.3% | 439 条 |
| 100 | 1183 | 19.7% | 697 条 |

★★ **结论：现行配置不满足「要一点操作 + 足够多配装方式」。**
125 的要求下 6000 次抽样只见到 5 条路 = 事实上的唯一解，玩家不是「挑」而是「猜」。
建议 scene_1 第 1 轮的 `contrast_req` 改成 **110**（214 条路 / 6.2%，离天花板还有 16 分）。

### 接受度不是瓶颈（这条容易走错路）

把 scene_1 第 1 轮的接受度 10 → 12 → 14 → 16（暴露上限 30 → 42）跑了一遍：

```
10/12/14/16 → DP 最优恒为 126，最优解只用 24/30 暴露
```

**放宽接受度完全无效** —— 卡住的是反差结构（top 那一格锁死），不是暴露额度。
所以「用户觉得太难」时不要先动接受度。

### 三套背景能到的上限差得很远

| 背景 · 轮 | 上限（DP 最优） | 现行要求 | 现状通过率 |
|---|---|---|---|
| scene_1 第 1 轮 | 126 | 125 | 0.1%（唯一解） |
| scene_1 第 2 轮 | 189 | 150 | **100%（白送）** |
| border_post 第 1 轮 | 193 | 125 | 64% |
| border_post 第 2 轮 | 294 | 150 | 79% |
| scene_2 第 1 轮 | 162 | 125 | 63% |
| scene_2 第 2 轮 | 232 | 150 | 58% |

同一个 125 / 150 不可能适配三套 —— 每套背景得写自己的 `contrast_req`
（`backgrounds[].levels[i].contrast_req`，编辑器「🎬 背景 → ⑦ 本局覆写 · 几轮」）。

## 三、测试怎么跟着改

`WardrobeTest` 有**三处按旧公式自己重算反差**（刻意的：「拿实现验证实现」没意义）：

1. `_expect_contrast()` —— 全槽位求和
2. `_walk_combos()` —— 枚举组合时的逐件期望值
3. 单槽位期望值断言（`top_lace` 那条）

三处都补上「同暴露值 + 不同件」那一档。★ 判「是不是原貌那件」用**物品 id**，
不是暴露值 —— 两个暴露值相同的不同件正是这轮要区分的东西。

新增两条断言：
- 「找得到同槽位 / 同暴露值 / 不同件的一对」（**防空转**：找不到就等于什么都没测）
- 「穿回原貌那一件仍然是 0 分」

★ 踩了个坑：`mm.true_appearance[slot] = ...` 报 `Invalid assignment on read-only value` ——
它可能直接指向 `OutfitData.TRUE_APPEARANCE` 这个常量。**整份 duplicate 后替换赋值**。

## 五、没做的事

- **没动 scene_1 的强制上装**（用户明确要求）。
- **没重拍截图**：布局没动，但反差数值变了 → 截图里的判定栏数字会变。
  等 `contrast_req` 定下来一起拍，免得拍两遍。
