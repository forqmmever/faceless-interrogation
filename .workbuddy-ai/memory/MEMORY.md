# 项目长期笔记（千面人 · 伪装与高压审讯）

## 工作流约定

### 改「文案」要同时找三处（第四十二轮）

改一句界面文案，**必须同时检查三个地方**，漏一个就出问题：

| 位置 | 为什么 |
|---|---|
| `ScenarioData.gd` 的 `DEFAULT_*` | json 缺失 / 解析失败时的兜底 |
| `data/story.json` | 游戏**实际读的**（它优先） |
| `tests/*.gd` 里引用它的**期望值** | 断言会挂（实测挂过 4 条） |

★ 而且**改了占位符数量就等于改了接口** ——
文案里多一个 `%d`，所有调用点的参数表都要补，否则运行时
「not all characters converted」。

### 术语「关 → 轮」是**精确模式替换**，不能全局替换（第四十二轮）

`关` 在中文里有太多无关用法。统一时必须用**模式表 + SKIP 词表**：

- 改：本关→本轮 / 这一关→这一轮 / 每关→每轮 / 上一关→上一轮 /
  下一关→下一轮 / 第 N 关→第 N 轮 / 关卡→轮次 / 几关→几轮
- **不改**：关口 / 关隘（地名）、通关文书 / 进关 / 过关（剧情动词）、
  关心 / 关键 / 相关 / 关闭 / 关注

★ 改完**复查 diff** 确认没误伤（实测只有 `第四关 · 关隘地牢前厅`
因含「关隘」被整行跳过，手工改前半、保留地名）。

★ 坑：脚本里 `line.split('#')[0]` 会把 BBCode 的 `[color=#8a919c]` 当注释起点 ——
**处理含 `#` 的颜色标记时别用 `#` 切注释。**

### 清理界面时的三条规矩（第四十二轮）

1. 删掉一个废弃节后，把冒烟测试里「它存在」的断言改成**反向断言** ——
   否则以后有人加回来，测试也不会响。
2. **「改标题编号」和「挪数组元素」是两件事** ——
   编号理顺了但元素位置没动，显示顺序照样乱。改完要回读渲染顺序确认。
3. 删掉的如果是**只读展示字段**，数据本身不受影响（仍在 json 里）——
   但要在注释里说清，免得以后以为数据丢了。

### 探针要跑真实链路，否则拿到假结论（第四十四轮）

第四十四轮要验「照片排除原貌后会不会导致无法过关」，第一版探针直接调
`RunData.start_new_run()` —— 得到 `revealed_slots = 0`，看起来像「原貌不可见」。

真相：`revealed_slots` 是**情报台（UI 层）**写进去的（`IntelDesk._fill_revealed()`
+ `sync_to_gamedata()`），不实例化场景就看不到。

**规矩**：验游戏行为时用 `load("res://scenes/Main.tscn").instantiate()` 起真实场景
（TestRunner 就是这么做的），别只调 autoload 的函数。

### 给「约束」写测试时，配一条对照断言（第四十四轮）

验「眼镜 / 发型 / 鞋子 各自最多一次」时，同时断言「**主体（上衣）不受这条限制**」。

理由：如果只验前者，那么「**所有**槽位都最多一次」这种写歪的实现也能让测试通过。
**对照断言才能证明规则是「特定于某些对象」的，不是一刀切。**

同理适用于任何「只对部分对象生效」的规则。

### 跨「批次」的约束要跑完整流程（第四十四轮）

照片是「开局 3 张 + 每轮 +2 张」逐轮追加的。
「整局各自最多一次」这条约束**只跑开局那 3 张是验不出来的** ——
必须逐轮 `advance_level()` 把整局跑完。

**规矩**：约束的作用域是「整局 / 全流程」时，测试也必须走完整流程。

### `_merge_phone` / `_merge_flat` 是**逐键覆盖**（第四十三轮踩到）

改了 `ScenarioData.gd` 里的 `DEFAULT_PHONE` / `DEFAULT_RULES` / `DEFAULT_UI` 默认值后，
**story.json 里的旧值会把它盖掉** —— 实测：改完 `album.cleared` 再跑 DumpStory 导出，
值还是旧的。

**要么直接改 `data/story.json`，要么把那个键从 json 里删掉**（删掉才会回退默认值）。

### 改文案占位符数量 = 改接口（第四十三轮）

文案里 `%` 的个数一变，**所有相关处都要跟着改**，顺着这条链找齐：

| 顺序 | 位置 | 说明 |
|---|---|---|
| 1 | 使用它的代码 | `_tf("key", [参数...], "默认")` 里的参数个数 |
| 2 | `ScenarioData.DEFAULT_*` | 出厂兜底 |
| 3 | `data/story.json` | ★ 它会**盖掉**默认值（见上一条） |
| 4 | **「占位符数量守卫」断言** | WardrobeTest 一处、手机编辑器冒烟一处 |
| 5 | 编辑器的字段表 | `PHONE_FIELDS` / `PH_EXPECT` 等 |

★ 第 4 条那两处守卫**正是用来防漏的** —— 第四十三轮它抓到了自己的更新，
  这说明「给文案加占位符守卫」这件事本身很值。

### 结构约束优于概率约束（第四十三轮）

相册要求「上半身不能出现鞋子、下半身不能出现头发/眼镜」。
做法不是「取完候选再筛一遍」，而是**按组取候选**（上半身只从 `PHOTO_UPPER` 取）——
这样越界在**结构上不可能发生**，不需要靠检查兜底。

**能做成结构约束的，就别做成概率约束。**

### ★ 术语：一局 / 一轮（用户 2026-10-15 明确定义，之后一律照此）

| 词 | 含义 |
|---|---|
| **一局** | 含一套背景 + 若干轮的那一整局 —— 点开始游戏之后的那一盘 |
| **一轮** | 一次换装 + 问答环节（代码里的 `level_index`） |

以前文档里「关」和「轮」混着用，**现在统一成「轮」**。
用户说「每局游戏能设置不同 X」时，意思是「挂在这套背景上的、这一局专用的 X」
（因为一局的身份就是「抽到哪套背景」）。

## 技术约定

### 改 `data/story.json` 的两条铁律

1. **不能用 `DumpStory.tscn` 重跑来「顺便更新」** —— 从 GDScript 常量导出的只有
   `rules` / `ui` / `levels` / `forced_rules` / `qte_plan` / `defects` / `catalog` /
   `backgrounds` / `traits` / `item_desc` 等；但 `backgrounds[].questions[]` 里
   第二十九轮迁移出来的题目**只存在于 story.json**，常量里没有备份。
   重跑一次就把题目全冲掉。**要用脚本精确改字段**。
2. 改完必须**重建编辑器快照**：`python tools/build_story_editor.py`（以及 `build_phone_editor.py`），
   否则编辑器里的内置快照与 story.json 脱节，冒烟测试会挂。

### 文本与逻辑的分界

- **文本**（短信 / 对话 / 题目 / 选项 / 结局 / 界面文案 / 数值规则 / 关卡）→ `data/story.json`，编辑器改
- **逻辑**（判定 / 求解 / 渲染）→ `scripts/*.gd`
- 改数值或关卡**要重标**：README 里记录着每轮的实测「可达反差下限」，改完数值曲线要对得上

### 测试与判定的写法

- **不要按「题目的类别」写断言** —— 第二十九轮起题目不再分类，一律从数据形状推
  （`_q_kind()` 这类助手）；`kind` 字段只在旧格式兜底路径里存在。
- **不要假设「第 N 题是什么」** —— 题序 = 题目清单顺序，玩家可在题库页拖。
  用「按类型现找」的助手，不要 `_load_question(1)` 写死。
- **断言要防「空转通过」** —— 读一个已废弃的数据段时循环一次都不进，
  计数器全 0，断言全绿但什么都没测。加一条「样本里确实查到了 N 条」的断言防这个。

### 写「单调 / 递增」类断言时，先把取样点的数值写下来核对

第三十三轮踩的：想验「暴露值越高 → 触发概率越大」，取了三 个点
`min+5 / 中点 / min+15` —— 第三个点（25）其实**比中点（35）还低**，
于是断言写成 `0.10 < 0.50 < 0.30`，当场挂掉。

> 规矩：写 `a < b < c` 这类断言前，**先在纸上算出三个取样点的实际值**。
> 名字叫 low/mid/high 不代表数值真的递增 —— 尤其是从「最小值 + 偏移」推出来的点。

### 派生数据不会自己跟上来（三处都是「改了源表还得手动同步」）

改 `OutfitData.gd` 的**槽位或标签**时，除了改那一行，还必须记得：

1. **重烘图包**：`data/doll*.json` 里每件物品的图层 `z` 是从 `OutfitData.gd` 的槽位推出来的
   （`dol_prepare.item_slots()`）。第 32 轮把两件丁字裤从 `panties` 挪到 `bottom` 但没重烘，
   于是预览里它们一直画在下装**下面**，谁也没发现 —— 直到第三十四轮重烘才修好。
2. **重建 `story.json` 的 `catalog`**：那是 `DumpStory` 导出的只读快照，
   而 DumpStory **不能随便跑**（会用内置常量覆盖 JSON，冲掉只在 JSON 里的题库）。
   所以它只会越漂越远 —— 第 32 轮的槽位、第 28 轮的标签都漂了。
   正确做法是**用脚本按 `OutfitData.gd` 重建 `catalog.items`**，别去跑 DumpStory。
3. **`tools/story_editor.html` 里另有一份手写的 `TRUE_POOL` 常量** ——
   它在 JS 常量区、**不在内嵌快照的两个标记之间**，所以 `build_story_editor.py`
   重建快照时不会碰它，必须手改（否则编辑器的「原貌候选池」和游戏对不上）。

> 一句话：**`OutfitData.gd` 是唯一权威，其余全是派生快照。**
> 改完权威表顺手问一句「哪些地方抄了它」。

### 新增物品后必须先让 Godot 登记资源

烘完 `assets/dol*/` 的新 png 之后要跑一次
`godot --headless --path . --import`。
不然 `ResourceLoader.exists()` 对新 png 返回 false，
WardrobeTest 的「全部物品均有卡片图标」会挂 —— 而烘焙产物其实是好的，
只是没被 Godot 写进 `.godot/imported/`。这个坑第三十四轮踩过一次。

### 只使用 AU 图包（第三十七轮定下的硬约定）

用户口径：「现在和之后只使用 au 源的服装」。这不是「挑衣服时优先 AU」，
而是**DoL 那条链路已经从代码里拆掉了**：

- 唯一图包 = `au`。`tools/dol_prepare.py` 的 `PACKS` 只有 `au` 一项、`--pack` 默认 `au`；
  `tools/dol_map.py` 用 `AU_OVERRIDE`（不再有 `PACK_OVERRIDE` / `PACK_HAIR` / `hue_shift()`）；
  `scripts/DolDoll.gd` 只有三个常量 `PACK` / `ROOT` / `DATA_PATH`。
- **产物只有一份**：`assets/dol_au/` + `data/doll_au.json`。
  `assets/dol/` 与 `data/doll.json` 已删除，**不要再把它们写回代码或文档**。
- 取景框只有 AU 那一套（68×203，画布 512×256）；`ScenarioData.PHOTO_FOCUS` 是唯一一张表
  （以前按 `DolDoll.pack()` 分两张）。
- 引用路径一律走 `DolDoll.root()` / `DolDoll.data_path()`，**不要写死 `assets/dol_au`**
  —— 写死会绕过「换图包」这层抽象，测试也会变成假通过。

### DP 选项剪枝的两条铁律（第三十七轮）

「一键达标」的门控组（top/bra/bottom/dress/panties）算的是**笛卡尔积**。
补到 155 件后原积到 62 万，DP 从 0.2 秒涨到 7~8 秒 —— 靠 `_dedupe_equivalent()` 两级剪枝压到 27。

1. **① 去重的键必须用「归一化后」的字段**，不能用 `tags` / `gate` 的原文：
   要用 `_defect_mask_of(it)` 和 `data.outer_slots_of_item(it)`。
   用原文的后果：`tags` 顺序不同、或 `gate` 显式写 vs 回落 的等价件漏过 ①，
   进 ② 又因为语义确实相同而**互相判定为被支配、双双被删**，
   整个槽位候选清空 → 该组无解 → 「一键达标」静默返回「什么都没改」。
   （第三十七轮实测踩过，WardrobeTest 7 条断言才抓到。）
2. **② 帕累托剪枝里四项全同时只能让一方赢**（按序号），绝不互删。
   另外必须在**同一「行为签名」组内**比（`outer_slots_of_item` + `see` + `is_bare`），
   否则会剪掉「自己数值差一点但能把别的槽位露出来」的必需件。

验证手段：`tools/PerfProbe.tscn` 这种一次性探针很好用 —— 直接量「每个槽位去重前后候选数」
与 `auto_complete_outfit()` 的平均耗时。写完记得删。

### 两条「槽位级名单」语义相反，别搞混（第三十九轮）

```gdscript
OutfitData.DISABLED_SLOTS   # 下架：玩家看不到
OutfitData.MANUAL_SLOTS     # 只能手动装备：玩家看得到、点得到，但系统从不代劳
```

| 表 | 界面可见 | 能手动穿 | 原貌 | 情报 | 相册 | 强制池 | 一键达标 | 数值统计 |
|---|---|---|---|---|---|---|---|---|
| `DISABLED_SLOTS` | 否 | 否 | 不抽 | 不问 | 不拍 | 不进 | 不动 | 不算 |
| `MANUAL_SLOTS` | **是** | **是** | 不抽 | 不问 | 不拍 | 不进 | **不动** | **不算** |

配套三个函数，**别混用**：

- `active_slots()` = `SLOT_ORDER - DISABLED_SLOTS` —— **界面口径**（换装界面遍历它）
- `auto_slots()` = `active_slots() - MANUAL_SLOTS` —— **自动流程 / 数值口径**
  （原貌 / 情报 / 相册 / 强制池 / 一键达标 / 一致数统计）
- `slot_enabled()` / `is_manual_slot()` —— 单项判断

★ 新加一个槽位时，**先问自己它属于哪一类**：
· 会出现在换装界面吗？→ 在 `active_slots()` 里（别误加进 `DISABLED_SLOTS`）
· 该被系统自动抽 / 自动算吗？→ 不在 `MANUAL_SLOTS` 里

★ 一次不一致就直接出假数字：`peek_hint` 的分子分母来自不同集合，
会印出「13 / 14 处仍一致」。**凡是「N / M」的显示，分子分母必须同一个集合。**

### 截图「变了」不一定是回归 —— 先过这三条判据（第四十轮）

第四十轮排查了两小时的一个假警报：`screenshots/19_expression_qte` / `20_leak_exposed`
与上次提交的版本不同，逐行怀疑 `RunData` 的随机流。一路二分（还原 RunData → 还原
OutfitData + ScenarioData → 连 story.json 也还原成 HEAD 版），
**结果代码全部回到 HEAD、这两张图依然不同** → 差异不是代码引起的。

真凶：跑过 `godot --import` 之后**导入缓存被刷新**，字体图集烘焙结果变了，
文字边缘的亚像素抗锯齿随之略有差异。

**判据（三条同时成立 = 抗锯齿差异，别当回归）**：
1. 同一份代码**连跑三次完全一致**（渲染本身是确定性的）
2. 差异是**稀疏点状** —— 把 diff 降采样成字符画能看出是文字边缘，不是整块 UI
3. 该镜头的 `_plog` 状态输出**逐字相同**（题目序号 / 进度 / 可见性）

★ 二分排查时**先做"代码全还原"这一步**，它一次性排除掉所有代码嫌疑，比逐个文件试快得多。

### 用字符画「看」图片差异（模型读不了图时的替代手段）

定位图片差异时，把 diff 降采样成 ASCII art 打印出来，能直接看出差异的形状：

```python
d = ImageChops.difference(a, b).resize((96, 27), Image.BOX)
ramp = ' .:-=+*#%@'
# 每个像素映射成 ramp[min(9, v * 10 // 256)]
```

「整块 UI 不同」会显示成大片 `#@`；「文字边缘」显示成稀疏的 `.::`。
第四十轮就是靠这个判断出「差异在左侧对话文本区、且是稀疏点状」。

### 纯函数测试测不出「时间线上的 bug」（第四十轮）

第四十轮两个 bug 都不是靠单元测试发现的，值得记：

1. **「假防御」** —— `RunData._normalize_true_exclusive()` 里 `for s in group` 遍历的是
   **嵌套**数组（`[["dress"], ["top","bottom"]]`），`s` 是子数组、`str(s)` 变成 `'["dress"]'`，
   `dict.get()` 永远查不到 → 整段是死代码，注释却写着「这是纯防御」。
   **发现方式**：给新功能写测试时顺手构造了能触发它的输入，当场挂。
2. **「粘关」** —— 未配覆写的关沿用了上一关的原貌（`true_app` 被覆写覆盖后丢了基础那套）。
   **发现方式**：写了**端到端探针**（手改 story.json + 跑真实流程 + 打印三关结果）。
   ★ 单元测试当时是绿的 —— 它只测 `_apply_preset()` 这个纯函数，
     没测 `start_new_run → advance_level → advance_level` 这条**时间线**。

**规矩**：涉及「状态随时间 / 关卡推进而变化」的功能，除了纯函数测试，
**必须再写一个走完整流程的探针**（哪怕临时、用完就删）。
判据：**测试里如果没出现两次以上的状态推进，它就测不到时间线。**

### 改「初始化顺序」前先 grep 谁依赖那个顺序

`start_new_run()` 里 `level_index` 原本在 `_roll_true_appearance()` **之后**才赋值。
第四十轮让原貌依赖 `level_index`（按关覆写）之后，这个顺序就成了 bug ——
「从选关面板直接进第 N 关」会取到上一局残留的关卡号。

**改初始化顺序前，先 grep「这段之后、那行之前」还有谁在用那个变量。**

### 测试用完一定要把「跨局保留」的状态清干净

`ProfileData.add_gain()`（接受度）是**跨局保留**的。第四十轮的用例反复调
`advance_level()`，把接受度永久推高了 → 后面「开局接受度 = START_ACCEPTANCE」当场挂。

规矩：用例里调过 `advance_level()` / 改过 `ScenarioData._*_presets` 这类**全局**状态，
**结尾必须显式还原**（`ProfileData.reset_all()` + 把改过的注入值清回 `{}`）。

### 运行时覆写：`static var` 是唯一解（第四十轮）

要让「一份 JSON 能在运行期改掉代码里的常量表」，有三个坑一次踩全：

1. **`const` 改不了**（编译期只读）→ 得改成 `var` 或 `static var`
2. **普通 `var` 又不行** —— 如果那张表被 `static func` 读，静态上下文够不着实例成员。
   **`static var` 是唯一解**：静态函数能用、实例方法能用、运行期能改，
   而且**原有的 `OutfitData.ITEMS` 写法一行都不用改**。
   ★ 连带：它依赖的缓存（`_by_slot` / `_by_id` / `_stat_max`）也要一起改 `static var`，
     否则 static 的失效函数够不着它们。
3. **必须「原地改容器」而不是「换一个新容器」** ——
   全项目有几十处**直接读** `X.ITEMS` 而不做函数调用，换表的话那些引用点还拿旧表。

时序上还要注意：**autoload 顺序决定谁读得到谁**。
`OutfitData` 在 `ScenarioData` **之前** ready，而数据在后者手里 ——
所以覆写要由 `ScenarioData._load_story()` 读完文件后**反调** `OutfitData.apply_*()`。
兜底函数里**绝不能**在「数据源还没就绪」时标记完成，否则会把空覆写当成最终结果、永远丢失。

### 覆写类数据的落盘约定（第四十轮）

`story.json` 里的 `item_overrides` 这类「覆写」段，**只写「与内置值不同」的条目**：
编辑器中把数值改回内置值时，**自动删掉这个字段**（两个字段都回到内置值就删掉整个 id）。

好处：文件干净（默认是 `{}`）、语义明确（**文件里有 = 改过**）、
校验里能直接报「这一条与内置值相同，是多余的」。

### 判「两张图是不是同一张」要用两个独立方法交叉验证

第三十八轮踩过：清点 `genitals` 的四种磨损态时，第一版用「逐像素数差异」
（`ImageChops.difference` 后按 alpha 阈值数点），得到一堆 0 和几个十几二十的小数字 ——
**很容易把「渲染噪声」和「真的不同」看混**。

规矩：结论要同时过这两关才敢写进文档 ——

1. **文件 MD5**：一致 ⇒ 绝对是同一张图（最硬的证据）
2. **`ImageChops.difference(a, b).getbbox()`**：返回 `None` ⇒ 逐像素一致

★ 也别只看**尺寸 / bbox**：图包里有大量「bbox 一样但内容不同」（以及「bbox 一样、
内容也真的一样」）的情况 —— 尺寸相同完全不能推出内容相同。

★ 反过来也一样：**名字像不代表内容一样，名字不像也不代表内容不同**。
实证 —— `props/npc/` 47 张拼起来是一个完整 NPC 立绘（不是道具）；
`chastitycage` 与 `chastitycagefetish` 两个目录名字不同但 `full.png` 完全相同。

### 稳定随机 vs 运行时随机

「同一道题要不要出 QTE」这种事，**必须用确定性哈希**（`hash("seed|关号|题号|标签")`），
不能用 `RandomNumberGenerator`。因为同一道题会被**反复装载**
（来回切题、重来本轮、测试里多次 `_load_question`）——
每次现摇会变成「同一题一会儿出一会儿不出」，玩家莫名其妙、测试也没法断言。

### 带反斜杠的 Python 脚本一律写成文件再跑（别用 heredoc）

Bash 的 heredoc 会把 `\\` 吞成 `\`。所以 `python - <<'PY' ... re.compile(r'[^"\\]') ... PY`
传进去的正则**已经被改坏**（`[^"\]` → `unterminated character set`）。
前几轮那些「看起来能用」的 heredoc 脚本其实也在被吞，只是刚好没炸。

> 规矩：脚本里只要出现正则、转义、Windows 路径反斜杠，就用 Write 工具写成
> `.workbuddy-ai/tmp/xxx.py` 再 `python xxx.py`。

### AU `bodywriting` 的位置集合有两套

- **14 个图案**（flower / star / heart …）有全套：`forehead` / `left·right-cheek` /
  `left·right-shoulder` / `left·right-thigh` / `breasts-0..6` / `pubic`。
- **`text/` 那 32 个短词**只有 **五个**：`forehead` / `left·right-thigh` / `breasts` /
  `pubic` —— **没有 cheek / shoulder**（`default` 例外，它全套都有，还带 `-arrow` / `-heart` 变体）。
- 两套**都没有 `neck`**，所以「颈侧刺青」只能借左肩（第二十六轮起的已知取舍）。
- 源图尺寸差异极大：`paw print` 5×5、`flower` 10×10、`heart`/`cross`/`flame` 那种
  大腿档是 14×78 的**竖长条** —— 挑图案时**必须逐个量 bbox**，不能照抄别人的 `scale`。
- ★ 第三十六轮起 `text/` 的四件刻字（bitch / free-use / slave / cum-rag）走的是**整字**路子：
  位置沿用图包自己的落点，`align` 由该部位字形 bbox 中心反算，只做小幅缩放（0.72 ~ 1.6）。
- ★ 那些 png 都是 **512×256 整画布**，左右两列各画一份 —— 探图脚本要自己过滤 x<130，
  否则会看到「一张图里好几个词」的假象（`clip_to_body()` 只负责烘焙时裁掉右列）。

### 多件槽位：`equipped` 的值有两种形态（第三十六轮起）

- `OutfitData.MULTI_SLOTS := {"tattoo": 2}` —— 只有纹身是多件槽位，其余槽位一件。
- `WardrobeModel.equipped` 的值：**单件槽位 = `String`，多件槽位 = `Array`**。
- **一律走访问器** `ids_at` / `id_at` / `has_id` / `set_ids` / `solid_ids` / `_ids_of`，
  不要再写 `str(equipped.get(slot, ""))` —— 多件槽位上那会得到 `["a", "b"]` 这种字符串。
- 多件槽位的「空件」必须标 `"bare": true`（`tattoo_none` 第三十六轮才补上），
  否则 `_settle_multi()` 会把它当成一件真货占名额。
- 门控也分了级：`OutfitData.outer_slots_of_item(item)` **先看这一件自己的 `gate`**，
  没有才退回槽位级的 `UNDER_GATE`。纹身按件写 gate（部位不同、遮盖不同），内衣内裤继续走槽位表。
- `_delta()` 的连带项扫 `OutfitData.gate_dependents(slot)`（静态缓存），
  并且**只在可见性真的翻转时**才重算那一槽位的贡献 —— 无条件重算会把 WardrobeTest 拖慢 3 倍。
- DP（一键达标）里多件槽位**故意不并进** `top/bra/dress/bottom/panties` 那一大块，
  自成一个单元素组、暴露值按保守口径计入（并进去选项数会从两万五涨到上百万）。

### GDScript 的坑（踩过的）

- **`arr or []` 非法** —— `or` 只吃 bool，会直接报错（表现为「打印到一半进程就没了」）
- **没有 `repr()`** —— 那是 Python 的
- **删跨行的 `print` 要连后半截一起删** —— 只匹配第一行会留下孤行 → Parse Error 且行号指偏
- **只读常量数组要整体 duplicate** —— 光 duplicate 元素不够，
  `_backgrounds[i] = bg` 这一步照样报 `Invalid assignment on read-only value`
- **★ 不支持单行 `if … else` 语句** —— `if x == null: a else: b` 直接 Parse Error
  （「Expected end of statement after expression, found "else"」）。
  只支持 `x if cond else y` 这种**表达式**形式；语句必须拆成多行。
- **`sort_custom` 是**不稳定排序** —— 需要「相同键保持原顺序」时必须
  自己带上原下标当第二键，否则同一批数据每次跑都可能换位置（偶发、极难查）。**

### 编辑大文件后要回读一眼

用脚本/编辑工具改完，**顺手 `sed -n` 回读改动处** —— 本会话出现过
「替换时把换行一起吃掉、两行合成一行」（GDScript 立刻 Parse Error，
但如果是 CSS/HTML 里的合并可能不会立刻报错）。
