# 第四十轮：服装数值编辑器 + 原貌编辑器

日期：2026-10-15

## 用户口径（原话）

> 「生成服装的暴露度和接受度编辑器，以及每局每关游戏的原貌编辑器，
> 能够从已有的服装选择组成原貌」

澄清（AskUserQuestion）：
- 原貌生效方式 → **两种都要**（随机池 + 按关覆写）
- 放在哪里 → **story_editor 加两个页签**
- 数据落点 → **写进 data/story.json 新段**

## 一、真正的工作量在游戏侧，不在编辑器

服装的 `exposure` / `acceptance_req` 原本**写死在 `OutfitData.gd` 的 `ITEMS` 里**。
一个 HTML 编辑器无论多好看都改不到它 —— 必须先打通数据通路。

两条新段：

| story.json 新段 | 形状 | 谁读 |
|---|---|---|
| `item_overrides` | `{id: {exposure, acceptance_req}}` | `OutfitData.apply_item_overrides()` |
| `true_presets` | `{pool: [{name, slots}], by_level: [{name, slots} \| null]}` | `RunData._roll_true_appearance()` |

## 二、`const ITEMS` → `static var ITEMS`（这步被逼的）

- `const` 编译期只读，运行期改不了
- 但换普通 `var` 也不行：文件里有 **15 处 `static func`** 在读 `ITEMS`
  （`bare_id_of` / `sheer_items` / `gate_dependents` …），静态上下文够不着实例成员
- **`static var` 是唯一解**：静态函数能用、实例方法能用、运行期能改
- 收益：全项目 **33 处 `OutfitData.ITEMS` 写法一行都没改**

★ 探针先验证过才动手（`static var` + 静态函数读 + 运行期改 + 改完直读）：

```
静态表直读（未 ensure）= 1
经函数访问（ensure 后）= 99
ensure 之后直读 = 99
static var 可改 = true
```

配套两个细节：
1. **覆写必须「原地改」**（`ITEMS[i][field] = v`），不能换新表 ——
   那 33 处「直接读不做函数调用」的地方才会自动跟上
2. 三张索引/满值缓存（`_by_slot` / `_by_id` / `_stat_max`）**同步改 static var**，
   否则 static 的 `_invalidate_item_index()` 够不着它们

## 三、时序：覆写不能放在 OutfitData._ready()

autoload 顺序：`GameData → OutfitData → ScenarioData → …`
→ **OutfitData 就绪时 story.json 还没读**。

所以由 `ScenarioData._load_story()` 读完文件后**反调** `apply_item_overrides()`。
另加 `_ensure_items()` 兜底（给绕过 autoload 直接用静态函数的场合）。

★ 坑：`_ensure_items()` 在「拿不到 ScenarioData 或 story 未加载」时**绝不能标记已完成**
—— 否则会在那一瞬间把空覆写当成最终结果，覆写永远丢失。所以它只在
`story_from_file == true` 时才标记 + 应用。

★ 另一个坑：`apply_item_overrides()` 里**不要**调 `_ensure_items()` ——
那会反过来拉 ScenarioData 的覆写，与「ScenarioData 正在调我」形成无谓递归。
直接 `_items_ready = true` 即可。

## 四、原貌三级优先

```
① by_level[本关] 有值  →  该关固定这一套（advance_level 时换，并重建情报）
② pool 非空            →  从整池随机抽一套
③ 都空                 →  老逻辑：逐槽位从 TRUE_POOL 独立抽   ← 默认就是这条
```

两个取舍：
- **「只写几件也算数」** —— 没写到的槽位继续随机抽，支持「只想钉死上衣和下装」
- **写空件是有效指定** —— 「他就是不穿下装」也是一种原貌

`by_level` 生效时切关要**重建情报**（`_maybe_apply_level_preset`），
否则情报台说「他颈侧有一片纹路」而人已经换了。
相册**不用重建**：照片只记槽位、显示时现查原貌，自动跟上。
已还原的槽位按槽位记（不按物品），换原貌后依然成立，玩家不用重查。

## 五、★ 顺带修掉一段「从没生效过的假防御」

`RunData._normalize_true_exclusive()` 声称防「原貌既有成装又有上装」。
但 `EXCLUSIVE_GROUPS` 是**嵌套**的 `[["dress"], ["top","bottom"]]`，
它写的是 `for s in group` → `s` 是子数组 `["dress"]` → `str(s)` = `'["dress"]'`
→ `true_app.get('["dress"]')` **永远查不到** → 整段是死代码。

它的注释还写着「当前 TRUE_POOL 里 dress 只放空件，所以这段平时不触发，是纯防御」——
真相是它**根本不工作**。（注释说得像「只是没到时候」，其实是「从来没对过」。）

修法：按模型层 `WardrobeModel._normalize_exclusive()` 的正确写法重写，分左右两组判。

★ **发现方式**：给新功能（原貌预设）写测试时，构造了一套「dress + top + bottom 全写」
的预设，断言归一化后只留成装 —— 当场挂了。
**给新代码写测试的价值，往往不在于测新代码本身。**

## 六、编辑器两个新页签

**👕 服装数值**（`view.kind === "items"`）
- 按槽位分组列全部 158 件，两个数字输入框
- 灰字 = 代码内置值；改过的行标黄；单行 `↺` + 顶上「全部还原」
- 搜索 + 「只看改过的」；下架槽位照列但压暗
- ★ 写入时**与内置值相同就删掉字段** → 「没改过的东西不在 story.json 里留痕」

**🎭 原貌**（`view.kind === "trueapp"`）
- 两模式：「① 随机池」（加/复制/删多套）与「② 按关覆写」（4 关，可一键按原貌池填满）
- 下拉带 `★` = 本来就在原貌候选池里
- 实时显示「指定了几个槽位 / 共几个」

`catalog` 导出新增两样支撑它们：`base_values`（内置值）与 `true_pool`（原貌池）。

## 七、坏数据一律跳过（不崩）

未知 id / 非数字 / 越界（暴露值 −1~12、接受度 0~99）/ 试图改槽位 → 全跳过 + push_warning。
测试里有一个用例把四种坏数据一起喂进去，断言「什么都没被改」。

## 九、新建的约定

- **`static var` 是「要让 static func 能读写、又要运行期可变」时的唯一解**
  （const 不行、var 不行）。改的时候连带把它依赖的缓存一起改 static。
- **覆写要「原地改容器」而不是「换新容器」** —— 否则绕过函数直接读容器的引用点会拿到旧值。
- **覆写类数据一律「与内置值相同就删条目」** —— 保持 JSON 干净、语义清晰
  （「文件里有 = 改过」）。
