## 换装系统（参考 WTS-1.46.1）

**参考来源**：`E:\Program Files (x86)\新建文件夹\WTS-1.46.1-pc-CHV2`（Ren'Py 引擎）
- 关键文件：`game/scripts/wardrobe/functions.rpy` → `get_outfit_score()`
- `game/scripts/doll/clothes.rpy` → `DollCloth` 类（含 `level` 字段）
- `game/scripts/characters/hermione/wardrobe.rpy` → 物品数据（203 个 `DollCloth(...)`）

**WTS 原版机制**：
- 每件物品有 `level`（暴露/解锁门槛，取值 0~19，常见 4/10/13/19）
- 角色有 `progression`（接受度），每关提升；装备门槛 `progress >= item.level`
- 暴露度评分 `get_outfit_score()`：每件 `level // 2` 累加；缺 bra +3、缺 bra 且缺 top 再 +6、缺 panties +6、缺 panties 且缺 bottom 再 +12；无 top +4、无 bottom +4；makeup +1、tattoo +2、piercing +3

**本项目实现**（3 个新文件）：
- `scripts/OutfitData.gd`（Autoload 单例）：服装库 `ITEMS`（28 件，8 个槽位）、缺陷 `DEFECTS`、关卡 `LEVELS`
- `scripts/WardrobeModel.gd`（`class_name WardrobeModel extends RefCounted`）：装备校验 / 暴露值上限 / 反差值判定 / 缺陷遮挡 / 关卡推进
- `scripts/Wardrobe.gd` + `scenes/Wardrobe.tscn`：换装界面（**纯代码构建 UI**，比手写 .tscn 更稳）

**三值设计**：
| 值 | 作用 | 公式/规则 |
|---|---|---|
| 接受度 acceptance | 每关后提升，决定能否装备高暴露衣服 | `clear_level()` 累加 `LEVELS[i].acceptance_gain` |
| 暴露值 exposure | 总和不可超上限 | 上限 = `6 + acceptance * 2` |
| 反差值 contrast | 与「推导形象」的差距，决定是否被直接识破 | 总和需 ≥ `LEVELS[i].contrast_req` |

**⚠️ 待确认的设计假设**：反差值方向由常量 `OutfitData.CONTRAST_HIGHER_IS_SAFER` 控制，当前设为 `true`（反差越高越安全，与用户"尽可能有差距"的表述一致）。若需反过来只需改这一个常量。

**取舍设计**：故意加入两类物品制造 build 深度 —— `acc_veil`（反差14/暴露2，高性价比但门槛9）与 `top_sheer`（暴露7/反差3，安全但吃暴露值）。

**主流程变更**：`Main.tscn` 的 `DisguiseSetup` 节点已被 `Wardrobe` 替换；`DisguiseSetup.gd` 成为无引用的死代码（体型调整功能暂未并入新换装系统）。

## 引擎选型评估（Godot vs Ren'Py）

**调研证据（对 WTS-1.46.1 源码的实测）**：
- WTS 的 `minigames/` 只有 4 类：cardgame（卡牌）、dueling（决斗）、puzzle（拼图）、mirror（镜子）—— **全部是回合制**，没有一个是实时操作。
- 全项目 `renpy.pause()` 调用统计：全是 **过场停顿**（`3.0` / `4.0, hard=True` / `12, hard=True`），没有一处是"限时输入判定"。
- 未发现任何"按住按键维持衰减条"类机制（`is_key_pressed` / `key_hold` / composure 均无匹配）。

**结论**：本项目核心的**实时表情 QTE**（长按维持镇定条、4 秒判定、衰减/增长）在 Ren'Py 生态里**没有先例**，属于要硬啃引擎的部分。

**建议：继续用 Godot。** 理由：
1. 实时 QTE 是核心玩法（不是装饰），Godot 原生支持；Ren'Py 的主循环是阻塞式 VN 流程，做这个要绕。
2. 规划中的"视线热力图"、多姿势、可能的 3D，都是 Godot 强项。
3. 已建成 57 项自动化断言 + 纸娃娃资产管线，迁移等于全部重写。
4. 换装数值系统是重逻辑轻文本，不是典型 VN 形态。

**什么情况下应该改用 Ren'Py**（触发条件）：
- 如果最终成品变成 80%+ 是阅读文本、QTE 只是点缀
- 如果最看重存档/回滚/文本历史/本地化/一键出多平台包（这些 Ren'Py 免费送，Godot 要自己写）
- 如果只有一个人做且不熟悉通用编程

**若留在 Godot 建议补的能力**：VN 对话系统可考虑 Dialogic 插件；存档、文本历史、自动播放需自建。

## 反差值语义重构：从「数值求和」到「与原貌的偏离度」

**用户反馈**：「衣柜同一阶段的收集和整理个人信息 按照尽可能与原本样貌相反的打扮的环节没有完成」

**问题诊断**：原实现里反差值只是把身上所有物品的 `contrast` 加起来，与「原本样貌」没有任何关系 —— "尽可能与原本样貌相反"这个目标在代码里根本不存在。同时「收集和整理个人信息」这一环节完全缺失。

# 第二轮 · 美术重制（日系赛璐璐）

**触发需求**：「人物 服装美术太简陋请生成更二次元的」

## 为什么不能直接用 AI 生图

换装系统需要 **18 个能自由组合、像素级对齐的图层**（穿环图层和内衣图层必须
在同一坐标系下严丝合缝，任何一个错位都会在叠图时露馅）。AI 生图每次的构图、
比例、位置都不同，做不到这一点。

→ **结论：把程序化渲染器整体升级到日系赛璐璐风格**，而不是换成贴图。

## 渲染管线 v2 → v3 的改动

| 维度 | v2（旧） | v3（新） |
|---|---|---|
| 超采样 | `SS = 2` | `SS = 3`（1080×1920 → LANCZOS 缩到 360×640）|
| 轮廓 | 硬折线多边形 | **Catmull-Rom 样条**平滑 |
| 填充 | 单一纯色 | **`gv/gd/gr` 渐变闭包**（纵/斜/径向）|
| 明暗 | 高斯模糊色块 | **`band()` 硬边赛璐璐明暗带** |
| 线稿 | 描边跟随多边形 | 独立线稿层 + 局部加粗 |
| 脸部 | 两个小椭圆眼 | **9 层二次元大眼** |
| 发型 | 一整块色块 | 颅顶发团 + 锯齿刘海 + 鬓角 + 天使环 |

**`Piece` 类新增 `self._ops`**：按**调用顺序**记录 `("sil"/"hole", sp, mask, bb)`，
`render()` 遍历 `_ops` 依次执行。
> **操作顺序即语义**：必须先 `hole(FACE_HOLE)` 挖脸、再 `sil(bang)` 画刘海。
> 旧版「先执行所有 sil、再执行所有 hole」会把刘海一起挖掉。

**渐变闭包签名从 `f(bb)` 改为 `f(bb, ub)`**（子形状 bbox + 图层并集 bbox），
t 按**图层自身**归一化。
> 旧版按整张画布 CH 归一化，导致图层高度只有画布 1/6 的物件几乎纯色，
> 而头发顶部会莫名变成浅色。

**`band(edge_pts, d0, d1=None, dy=0.0)`**：沿一条边缘点列生成「渐变收窄」的
明暗带（内缘顶点按 `t = i/(n-1)` 在 d0→d1 之间插值）。这是赛璐璐明暗的标准做法 ——
硬边、无模糊。

## 本轮踩的坑（12 个，按严重程度排）

1. **刘海被挖洞擦掉（最隐蔽）**：头发图层在 y=70..100 区域 alpha=0，刘海完全消失。
   用 ASCII dump 逐行检查 alpha 才定位到。
   → 根因是 `render()` 的「先全 sil 后全 hole」顺序。改成 `_ops` 顺序执行。
2. **阴影糊成一片**：body 里大量 `blur=S(2)/S(3)`，出来是渐变不是赛璐璐。

3. **渐变按整张画布归一化**：小物件几乎纯色、头发顶部变浅色。

5. **头发像马蹄形头盔**：颅顶发团太宽太厚、`FACE_HOLE` 太窄。

# 第四轮 · 文本数据外置 + 可视化文本编辑器

用户要求：「生成修改短信文本和对话 疑问 选项相关文本的编辑器」

## 一、关键决策：文本外置成 data/story.json

**没有**做成「编辑器去改 GDScript」。改 GDScript 文本太脆（转义、缩进、字面量语法），
所以把文本数据抽出来：

```
data/story.json          ← 游戏优先读这个（编辑器改的就是它）
      ↓ 读不到 / 解析失败
ScenarioData.gd 的 DEFAULT_* 常量   ← 出厂兜底
```

`ScenarioData.gd` 的改动很小、但有个必须记住的写法：

```gdscript
const DEFAULT_BACKGROUNDS := [ ... ]     # 原 const BACKGROUNDS，改名
var BACKGROUNDS: Array:                  # 属性 getter，懒加载
	get:
		_ensure_story()
		return _backgrounds
var _backgrounds: Array = []
func _ensure_story() -> void:
	if _story_loaded: return
	_story_loaded = true      # ★ 必须先置位，否则 _load_story 里读属性会无限递归
	_load_story()
```

六个属性都这么写：`BACKGROUNDS` / `INTERROGATOR_TRAITS` / `ITEM_DESC` / `CLUE_FRAME` /
`CLUE_SOURCES` / `PHOTO_NOTES`。

**逐段覆盖 + 逐段回退**：先装 `DEFAULT_*`，再让 JSON 里存在的段覆盖上去。
文件缺失 / 打不开 / 解析失败 / 某段是空的 → 那段退回默认。所以**删掉 story.json 游戏照样跑**。

新增 `story_from_file: bool`，测试里打印「数据来源」用。

## 二、JSON 生成与规范化

- `tools/DumpStory.tscn/.gd` —— 把 `ScenarioData` 当前值导出成 `data/story.json`。
- **`JSON.stringify(data, "\t", false)`** —— 第三个参数 `sort_keys` 默认为 **true**，
  会把键按字母序重排（`cards` 跑到 `id` 前面），读起来对不上源码。必须显式传 `false`。
- **浮点会被写成整数**：GDScript 的 `-2.0` → JSON `-2`，解析回来是 int。
  所有读取点都走了 `float(...)`，所以无害。**别依赖 JSON 里的数值类型。**

## 三、编辑器（tools/story_editor.html，单文件零依赖）

- 左目录（4 套背景 / 审问者性情 / 全局文本）+ 右侧 **schema 驱动的表单**。
  字段类型：`text / area / num / bool / select / strlist / objlist / strmap / strarrmap`。
- **嵌套 objlist 用 `fieldsFor(item)` 而不是静态 `fields`** —— 因为
  「同行者选项的 `value` 候选」依赖它所属那条 `companion_question` 的 `fact`。
- 每条条目 `👁` 就地预览（手机气泡 / 选项与代价 / 🌱 plant）。
- **实时交叉引用校验**（常驻顶部校验条）：题目指向的卡片、选项指向的版本、
  短信揭示的事实、`clue_frame` 是否含 `%s`、`ITEM_DESC` 是否覆盖 35 件候选池……
  都能点着跳过去。**这是编辑器最有价值的部分** —— 改坏了当场看得见。
- 撤销栈 80 步（Ctrl+Z / Ctrl+Shift+Z）、Ctrl+S 保存、Ctrl+F 搜索。
- 存盘：`showSaveFilePicker` 就地写回 `data/story.json`；浏览器不给权限时退化成下载。
- 「📋 回退常量」把当前数据导出成可直接粘回 `ScenarioData.gd` 的 GDScript 字面量
  （`JSON.stringify` 的输出**本身就是合法 GDScript 字面量**，省了一个序列化器）。

## 十五、第十轮：盲区题（「完全没给信息的题」）

用户原话：**「『完全没给信息的题』还是备忘录给的审问者信息推断出怎么答 继续」**

### 1. 口径（关键，别理解偏）

**不是**「给手机加一条线索让玩家去查」，**而是让备忘录里已有的审问者信息成为推断依据**。
所以盲区题的判定**不做「查资料」**，只做「你有没有读备忘录」。

这条需求在更早的「后续可扩展方向」里写的是「靠 `GameData.known_facts` 比对」，
本轮按用户这次的原话落在**备忘录第一条的审问者信息（性情）**上 —— 两者不要混。

### 2. 设计：新增一类 `kind = "blind"` 的题

- 档案里没有、短信里也没提 —— 题面**不指向任何卡 / 事实**（`card` / `fact` 都为空）；
- 所以它**没有「内容上的正确答案」**，三个选项固定是 **硬答 / 撒谎 / 回避**；
- **硬答恒定重罚** `BLIND_MADE_UP_DELTA = 18.0` —— 编得越细，他越能顺着往下追问。
  这条与性情无关（跟脾气没关系，纯粹是「说细节就露馅」）；
- **撒谎 vs 回避的代价由性情决定**（`trait_delta`），**正解 = 代价更低的那一个**。
  于是「正解」天然就是「备忘录里写着的那条对策」；
- 题面（`setup`）与题目标签都要**明说「这题你没底」**，否则玩家会以为是档案题去翻一张不存在的卡。

### 3. 一局 4 关不重复

第 `li` 关固定用 `blind_questions[li]`（每套背景 4 条）。既天然不重复，又方便测试与复现。

### 2. 机制：底部常驻占位带（`strip_band`）

解法：在 `root` 末尾放一个**永远存在的空 `Control`**（`STRIP_BAND_H = 96`），
把选项区顶到提示条之上；因为**常驻**，所以不会随提示条出现而抖。

**关键简化：两条提示条互斥 → 共用同一层。**
- `_start_interference()` 开头加护栏 `if is_qte_active: return`
- 于是 `INTF_FROM_BOTTOM == QTE_FROM_BOTTOM == 16`，占位带只需 **96** 高
  （原来按两层算要 200+，720 的屏根本放不下 —— 选项区 + 题面 + 反馈最小已吃掉 480）

  但 4 件 scale 全按 AU 几何重算（以前只覆盖了 `piercing_brow`）。

### 2. ★ 刺青改 AU bodywriting —— 坑是 scale 要多除一次 1.5

| id | 图案 | 尺寸 | 落身率 |
|---|---|---|---|
| `tattoo_neck` | `bodywriting/flower/left-shoulder` | 8×10 | 100% |
| `tattoo_cheek` | `bodywriting/star/left-cheek` | 7×8 | 100% |
| `tattoo_thigh` | `bodywriting/flower/left-thigh` | 15×15 | 96.5% |

`transform()` 里 `s = scale × align_scale`，`align_scale`(au)=1.5 是给「从 DoL 几何借来的贴图」用的；
bodywriting **本来就是 AU 几何** → 再乘一遍 = 平白放大 1.5 倍。初版 `scale: 1.333` → `s=2.0` →
一大半悬在身体轮廓外（身体掩膜实测：颈侧 65% / 颊 76% / 大腿 81%）。
**判据**：烘好的图层与「基础层并集」求交算**落身率**，<100% 就是位置/尺寸不对。
扫尺寸取「仍然 100% 落在掩膜上」：颈侧 s=1.0→100%（选它）/ 1.25→87% / 2.0→65%；
颊 s=1.5→100%；大腿 s=1.5→96.5%。
**反向半坑**：`transform()` 是对**已裁到全身像那一列**的图缩放再按 bbox 重新居中 →
**位置恒定、只有尺寸变**；拿 512×256 整张精灵模拟会得出「放大就飞出贴图」的错误结论。
**已知取舍**：AU bodywriting **没有 neck 位置** → 「颈侧刺青」只能落最近的 `left-shoulder`。

### 2. ★ `dress` 改名「成装」+ 与上装/下装互斥

```gdscript
const EXCLUSIVE_GROUPS := [ [["dress"], ["top", "bottom"]] ]   # 二分互斥
```

**★ 为什么不是「组内只能有一个」**：第一版把三者塞一个组做「只留一个」→ 开局原貌的
上装与下装被一起归零、反差不再是 0、一键达标整片挂掉。「上装+下装」本来就要一起穿，
真正的互斥只有「成装 ↔ 上装/下装」这一对（成装上半截=上装、下半截=下装）。

互斥落地四处：`equip()→_apply_exclusive()`（后装备的赢 + `_exclusive_stash` 还原）、
`_equip_defaults()→_normalize_exclusive()`（左边优先）、DP 的 `_walk_options` 剪枝、
`_counts_with()→_covered_by_exclusive()`（被顶掉的槽位整件不计入，否则白吃空件的 9 点暴露）。

**★ 原貌池 `dress` 只留空件**（`TRUE_POOL["dress"] = ["dress_none"]`）：原貌是「每槽位一件」的表，
而互斥意味着两种互斥穿法 → 让实体成装入池就得归一化，落败方压成空件反而白送数值、
情报台还会报两条矛盾目击。→ A 的原貌永远「上衣+下装」，成装留给玩家主动穿。
句式 `CLUE_FRAME["dress"]` = `「他%s。」`（★ 记得同步 story.json，运行时优先读它）。

  `neck_brand` 不触发（颈饰也能遮，集合 {top, neckwear}）。

  `_solve_with_forced` 与 TestRunner 的 `_build_viable` 都改成 `auto_complete_outfit()`。

## 第二十九轮：阶段二题目「不再分类」，改成可逐题编辑的清单（2026-10-14）

用户口径：「阶段二的问题我想不再给问题分类，直接让我编辑对问题进行编辑，如问题的 qte 出现时间，
qte 类型，问答，选项，触发游戏结束，问题的个数，是否触发抖动，选择选项之后怀疑值的怎么加多少吗等，
但后续可能还会做自动生成整局游戏内容，怎么搞比较好」

### 0. 三个决策（用户全选推荐方案）

① `facts` 保留为**可选骨架**（题目可挂可不挂）；② 本轮只做 **schema + 逐题编辑器**，生成器留接口下轮做；
③ 生成方式定为**程序骨架 + LLM 填词**。

### 1. 诊断：分类分在哪

- 题目**不是清单**，是 `RunData.questions_for_level()` 里 42 行**编排代码**按固定位置拼的
  （第 3 道固定同行者、第 6 道固定盲区、第 7 道固定跨关复问）
- 一题有**四套互不相同的 JSON 结构**（`questions`/`facts`/`companion_questions`/`blind_questions`）
- QTE / 抖动 / 怀疑值绝大多数写在全局常量与代码里（只有 `qte_plan` 可按题号覆盖，而它一直是空的）

### 2. 统一 schema（`backgrounds[].questions[]`）

每题：`id`/`level`(0..N 或 -1=通用池)/`speaker`/`text`/`setup`/`card`/`fact`/`recall`/`plant`/`qte{kind,delay}`/`options[]`
选项：`text`/`tone`/`suspicion`(可空=继承全局)/`value`(仅 version)/`ending`
**七种 tone**：correct / leak / version / bluff / evade / silence / made_up

两条原则：**一切可缺省**（`suspicion` 留空=仍按「档案卡归属+性情」老规则算）、**纯数据无耦合**（判定只看 tone）。

### 3. 出题规则

`level == li` → 本关固定题（按清单顺序）；`level == -1` → 通用池补足到 `questions_per_level`；
`recall: true` → 按本关抽到的旧说法挑对应题。**顺序 = 清单顺序**（拖顺序改节奏的前提）。
迁移结果（每套 24 道）：通用池 12（8 档案+4 复问）+ 每关 3 → 每关 3+1+4 = 8 ✓

### 4. 运行时改动极小

**判定逻辑一行没改**（`_select_option` 及下游原样）—— 新代码只把 `tone` 翻译成原来那套内部字段。
新增 `_build_unified_options`；`questions_for_level` 新格式优先、旧路径兜底；
`_q_text`/`_q_is_companion` 兼容新旧字段名；**题目自带 `qte` 优先**于按题号的全局计划表。

### 5. 编辑器 + 校验器

新增「🗣 题库」页（逐题编辑全部字段 + 嵌套选项列表）；`bgSections` 旧三节合并成提示。
校验器（编辑器与生成器共用）查 id 唯一/level 范围/tone 合法/选项文本/version.value 在事实表/
引用存在/同行者必须有「顶回去」选项/盲区题必须答得出来/每关题量够不够。

### 6. ★ 校验器当场抓出迁移脚本两个真 bug

① 同行者「不表态」选项 value 为空却标成 version（应是 evade，标错会参与一致性检查算出错结论）
② 某盲区题「硬答」本来就空（合法）却被生成成空文本选项（盘问里会出现空按钮）

### 7. 坑

- **测试里到处是「第 N 题是什么」的硬编码**（`_load_question(1)`）→ 改按类型现找。
  散布在**五处**：TestRunner / WardrobeTest / 编辑器冒烟 / 手机冒烟 / 截图脚本
- **`Array or []` 在 GDScript 里非法**（or 只吃 bool）→ print 参数求值直接报错，
  表现为「打印到一半进程就没了」，查了好几轮才定位
- **GDScript 没有 `repr()`**；**删跨行 print 要连后半截一起删**（否则孤行 → Parse Error 且行号指偏）
- **`bgSections` 旧分区要一起删**（迁移删了 companion_questions 段 → arr() 返回 undefined → 冒烟崩）
- ★ **断言「空转通过」比失败更隐蔽**：同行者问答那段读旧段，循环一次都不进、计数器全 0 →
  断言全绿但什么都没测。改完加了一条「样本里确实查到了」的断言防回归
- `_companion_option_index` 的 kind 假设：新 schema 下「不表态」项的 kind 是 evade 不是 companion
- **QTE 计划表按题号索引**，题序一变测试就错位 → 改成按实际题号生成计划
