### ② 手机：修「切换到相册界面大小会变」

**先量再改**（写了 8 版探针，过程见「踩坑」）：

- 手机**外框**在四个界面下都恒定：headless 336×607 / 真实渲染 336×582 —— 从来没变过。
- 真正的差异在**屏幕内容区的实际宽度**：消息页 **296** / 相册页 **299** / 备忘录 **296**。
  切到相册时整块内容会横跳 3px。
- 根因：**纵向滚动条一出现就占 3px 宽**。谁需要滚动条取决于内容长度，
  于是「切 App」变成了「内容区变宽变窄」。

**修法**：把纵向滚动条的宽度压到 0 —— 真机上的滚动条本来也是浮在内容上的、不占布局。
```gdscript
var vbar := scroll.get_v_scroll_bar()
vbar.custom_minimum_size = Vector2(0, 0)
vbar.add_theme_stylebox_override("scroll", StyleBoxEmpty.new())   # 连同四态样式一起清空
```
**验证**：修后四个界面内容区宽度去重后 `[296]` —— 全部一致。

## ★ 踩坑：Godot 隐藏状态下不排版，会量出假数据

排查②时前 7 版探针都读到 `ScrollContainer 高 0 / 相册网格 0×0` 这种「布局彻底坏了」的数据，
一直找不到原因。真相是：**探针没有真正开局，衣柜是隐藏的（停在标题界面）**，
而 Godot 对隐藏分支不做排版，于是所有容器都停在「按最小尺寸排过一遍」的状态。

- 判据：连抓两张截图（消息页 / 相册页）**md5 完全相同** —— 说明手机根本没画出来。
- 修法：探针必须照 `Screenshot.gd` 的做法先 `main._start_new_run(seed)` 再开手机。
- 修后真实数据：相册网格 **291×800**，一切正常。

> 教训：**用探针量 UI 之前，先确认这条分支真的在显示**。
> 「0 高度 / 0 尺寸」这种极端值，先怀疑是隐藏状态，别急着改布局代码。

其它踩到的 Godot 细节：
- `Control.minimum_size_changed` 是**信号**，方法叫 `update_minimum_size()`。
- `var main := load("...").instantiate()` 推断不出类型 → `var main: Node = ...`。
- `queue_sort()` / `update_minimum_size()` 对**已经陈旧**的容器链无效，
  只有真正改变某层尺寸才会触发重排。

## ★ 踩坑：用 Python 重写文件会改掉行尾符（CRLF → LF）

本轮第一次提交时，`git show --stat` 显示 `scripts/Wardrobe.gd` 改了 **1751 行**，
而实际改动只有 43 行。原因：这两个文件原本是 **CRLF**，我用
`io.open(p,'w',encoding='utf-8',newline='\n')` 重写，把整个文件转成了 LF →
git 认为每一行都变了。

**判据**（一行就能查）：
```python
old = subprocess.run(["git","show","HEAD~1:"+f], capture_output=True).stdout
old_crlf = old.count(b'\r\n'); new = open(f,'rb').read(); new_crlf = new.count(b'\r\n')
# old_crlf > 0 and new_crlf == 0  → 被转成 LF 了
```

**处理**：本轮把这两个文件的换行改回 CRLF 后 `git commit --amend`，diff 收敛到 43 行。

**以后改文件时的规矩**：
- 项目里 `.gd` 的行尾**不统一**（有的 CRLF 有的 LF），别假设。
- 用 Python 改文件时，**先读原文件判断行尾**，再按原样写回；或者干脆用 Edit 工具
  （它不动行尾）。批量替换脚本要用 `newline=''` 并保留原行尾。
- 提交前扫一眼 `git show --stat`：某个文件的行数远超预期，八成是行尾符或编码被改了。

## ② 反差值换算法（用户选「与相册逐件比暴露度差」）

**老算法**：逐槽位累加物品自己手填的 `contrast`（与原貌相同则记 0），全部 15 个可见槽位参与。

**新算法**（`WardrobeModel._contrast_of`）：
```
反差 = Σ（只算 top / bottom）  |exposure(你穿的) − exposure(原貌那件)| × rules.contrast_per_exposure
```
- 基线取 `true_appearance` —— 相册那几张「偷拍」拍的就是 A 平时的样子，
  所以「穿了与相册记录相同的件 → 差 0 → 不计反差」是**自然得出的**，不用额外判断。
- 取绝对值：比记忆里露得多、捂得多都算偏离。
- 系数 `contrast_per_exposure`（出厂 5）是新加的规则项（rules 33 → 34 项）。

**收口点只有两处**（DP / 贪心 / 界面本来就走这两条）：
- `_contrib(slot, id, "contrast")` → 改走 `_contrast_of`
- `_contrast_in_slot(slot, it)` → 同样改走 `_contrast_of`
（`_delta` 建立在 `_contrib` 上，所以增量路径自动跟着变。）

## ③ ★ 必须重标：新算法把可达范围压低了

120 个种子实测（用真实求解器 `auto_complete_outfit`，把 contrast_req 临时压到 0）：

| | 第 1 关 | 第 2 关 | 第 3 关 | 第 4 关 |
|---|---|---|---|---|
| 老算法可达 | 45~48 | 60~69 | 60~69 | 60~69 |
| **新算法可达** | **30~40** | **40~75** | **40~75** | **40~75** |
| 老要求（20/30/40/50） | ✔ 余 10 | ✔ 余 10 | 余 0 太紧 | **✗ 无解** |
| **新要求（24/27/30/33）** | 余 6 | 余 13 | 余 10 | 余 7 |

★ 为什么新算法可达更低：只算上衣与下装两件，而老算法累加 15 个槽位。
上限反而更高（75 vs 69）是因为系数 5 把「9 档暴露差」放大成 45 分。

标定按「最差种子留 6 点余量」→ 曲线改成 **24 / 27 / 30 / 33**
（自增 `contrast_req_base 24 + contrast_req_step 3`，走第二十九轮那套自增机制）。
