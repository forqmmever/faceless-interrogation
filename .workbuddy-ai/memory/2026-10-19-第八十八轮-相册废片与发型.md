# 第八十八轮：相册废片预算 · 上半身必带发型

日期：2026-10-19　提交：`第 88 轮：相册废片预算 · 上半身必带发型`

## 用户口径（原话）

> 「第一轮中相册中的照片，无法恢复的不能超过两个，之后新增的无法恢复的不超过一个，
> 出现上半身时，发型要显示并且与原貌保持一致」

两句是两件事：① 废片（擦满也看不清）的**上限**；② 上半身照片**必带发型**且是原貌那件。

## 一、先把「无法恢复」定义清楚

`_make_photo()` 里三个数一次抽定：

| 数 | 取值 |
|---|---|
| `start_clarity` | `0.10 + randf() * 0.45` → 0.10 ~ 0.55 |
| `max_wipes` | `1 + randi() % 3` → 1 ~ 3 |
| `PHOTO_WIPE_STEP` | 0.25 |

`final_clarity = start + max_wipes × 0.25`，`< PHOTO_CLEAR_AT(0.70)` 就是废片。

**天然废片率 ≈ 1/3**（这是决定「这条限制会不会咬到」的关键数）：

| 擦几次 | 概率 | 需要 start ≥ | 落空概率 |
|---|---|---|---|
| 1 | 1/3 | 0.45 | 0.35/0.45 ≈ 0.778 |
| 2 | 1/3 | 0.20 | 0.10/0.45 ≈ 0.222 |
| 3 | 1/3 | −0.05 | 0 |

→ 1/3 × (0.778 + 0.222) = **0.333**

所以：开局 3 张全废 ≈ 3.7%、每轮 2 张全废 ≈ 22% —— 预算会真的被触发，
不是「反正也碰不到」的摆设。（实测 12 种子 × 5 张 = 60 张里 23 张废片，比例对得上。）

## 二、实现：预算按「批」重置

`RunData` 新增成员 `_photo_dead_budget: int`，在 `_append_photos()` 开头赋值：

```gdscript
func _append_photos(n: int) -> void:
    _photo_dead_budget = ScenarioData.PHOTO_DEAD_START if photos.is_empty() \
        else ScenarioData.PHOTO_DEAD_PER_LEVEL
    for i in n:
        photos.append(_make_photo())
```

- ★ **判据是「`photos` 空不空」，不是「第几轮」**。
  `_roll_photos()` 先 `photos = []` 再调 `_append_photos()` → 开局必然走 2 那支；
  `advance_level()` 追加时相册已非空 → 必然走 1 那支。
  **不需要给 `_append_photos()` 加「第几轮」参数**（加了反而多一处要同步）。
- 预算**按生成顺序消耗**（先到先得），不是「回头挑最差的两张留着」。
  对玩家可见的保证（废片 ≤ N）完全等价，但不用回头改已生成的照片。

`ScenarioData` 新增：

```gdscript
const PHOTO_DEAD_START := 2         # 开局那批最多几张救不回来
const PHOTO_DEAD_PER_LEVEL := 1     # 之后每批最多几张救不回来
```

## 三、兜底为什么只改擦亮次数

预算用完时两条路：

| 做法 | 代价 |
|---|---|
| **重抽这张照片** | ① 白吃一个「点缀名额」（`_photo_used_one_of`，眼镜/鞋子整局只有一次）② 多走随机数 → 同种子整局都变 |
| **只把 `max_wipes` 抬够**（本轮选的） | 只动一个整数，随机流不多走一步 |

```gdscript
var final_c := minf(1.0, start + float(wipes) * ScenarioData.PHOTO_WIPE_STEP)
if final_c < ScenarioData.PHOTO_CLEAR_AT:
    if _photo_dead_budget > 0:
        _photo_dead_budget -= 1
    else:
        wipes = _photo_wipes_to_clear(start)
        final_c = minf(1.0, start + float(wipes) * ScenarioData.PHOTO_WIPE_STEP)
```

`_photo_wipes_to_clear(start)` = `clampi(ceil((0.70 − start) / 0.25), 1, 3)`。

★ **一定有解**，因为最坏 `0.10 + 3 × 0.25 = 0.85 ≥ 0.70`。
但这是**算出来的前提、不是天生的**，所以补了守卫断言（见第四节）——
否则以后谁调小 `PHOTO_WIPE_STEP`，就会变成「预算以为补上了、照片照样是废片」的**静默失效**。

★ 返回字典里原来是一行重算表达式，本轮改成先算 `final_c` 再放进去 ——
**别在两处各算一遍**（改了一处忘另一处就是这个 bug 的形状）。

## 四、发型：退出「整局最多一次」名单

第四十四轮：`PHOTO_ONE_OF := ["glasses", "hair", "shoes"]`，整局各自最多一次。

**和本轮口径直接冲突**：一局 2 轮有 2~3 张上半身，按整局一次算只有第一张有头发。

改法（三处）：

```gdscript
# ① ScenarioData
const PHOTO_ONE_OF := ["glasses", "shoes"]      # 发型退出

# ② _make_photo() 槽位分组循环里，在 PHOTO_ONE_OF 判断之前
if slot == "hair":
    continue                                     # 既不进主体，也不占点缀名额

# ③ cand 组装完之后单独补
if half == ScenarioData.PHOTO_HALF_UPPER:
    cand.append("hair")
```

显示的那件**直接取 `true_item("hair")`**（第四十四轮就已经是这样，
`shown = true_item(slot) if slot == "hair" else _shown_item_near(slot)`）——
本轮只是让它在**每一张**上半身照片上都成立。

### ★★ 副作用：随机流整体偏移

上半身的 `cand` 现在**永不为空** → 不再走「一件都没选中 → 补一件」那条兜底 →
**少消耗一次 `randi()`** → 同一颗种子之后抽到的东西全变了。

实测（截图三方对照）：与 HEAD 代码重跑比，盘问相关的 13 张截图都差 1.5~4%，
差异全在文字区 —— 是**题目顺序换了**，不是画面坏了。
（相册那 2 张差 2.3% / 1.7%，是发型真的显示出来了。）

这个副作用**不可避免**（任何改动照片内容生成的改动都会挪随机流），也不必避免。

辅助函数（放在 `_test_photos_v2()` 后面）：

```gdscript
func _dead_count(from: int, to: int) -> int:
    var n := 0
    for i in range(maxi(0, from), mini(to, RunData.photos.size())):
        var p: Dictionary = RunData.photos[i]
        if float(p.get("final_clarity", 0.0)) < ScenarioData.PHOTO_CLEAR_AT:
            n += 1
    return n
```

★ 空照片（`_make_photo()` 返回 `{}`）**不需要额外守卫** ——
`_test_photos_v2()` 早就有「第 %d 张一件都没有」的断言，真出现空照片会先在那里红。

## 六、跑测试的实况（重要：HEAD 数据已经脏了）

★★ **这一轮踩到的坑**：以前用 `git worktree` 拿 HEAD 干净数据做基线，
现在 **HEAD 自己就是脏的** —— 第 86 轮的提交把用户当时工作区的 `story.json` 一起提交了：
`border_post` 是 `enabled:false`、新增的 `bg_new_1` 是空背景、两套 `scene_*` 都是 `manual`。

后果（都是**数据问题、不是代码问题**）：

- `TestRunner._canonical_bg()` 找「`questions_source != manual` 的启用背景」→ **返回空**
  → `_start_new_run(-1, 0, "")` 用**毫秒时间戳**当种子 → **随机**挑到 `scene_1` 或 `scene_2`。
  于是同一份代码跑两次，失败数会在 **71 / 73** 之间跳（`scene_2` 的题数不够）。
  ★ 这不是本轮引入的，但**以后每轮都会遇到** —— 判「新增失败」时必须先看
  「`★ 本测试钉在一套「完整档案」背景上（实际 scene_X）`」这一行确认挑到了谁。
- `TestRunner.gd:150` 报 `SCRIPT ERROR: Out of bounds get index '0'`（0 张卡的背景上取 `cards[0]`）
  → 之后约 60 条断言**静默消失**。
- `editor_smoke` 的 42 条失败全是校验器在报用户数据。
